## 一、研究目标与主要结论

用户真正想完成的不是阅读大量 ChangeEvent 或 0/8、2/8 的统计，而是：

1. 今天哪个我方商品组应该优先检查，具体哪家公司做了什么？
2. 某个商品组内，以**公司名称为主身份**，按价格、MOQ、SKU、成交、上架日期、评价、标签等指标筛选排序，明确**我方在可比较商品中的位置**。
3. 对手最近的调价、上新、修改 MOQ/SKU 等动作发生后，公开可见的经营表现有什么变化？
4. 这个品是否有发展潜力？这是**市场样本 + 需求趋势 + 我方利润**问题，不是人工选择 8 个竞品即可解决的问题。

核心研究结论：

- **店雷达**：借鉴 1688 商品/商家字段体系及筛选、竞店动作证据。
- **Jungle Scout Product Tracker**：借鉴同组商品对比、可配置列、组级摘要和历史视图。
- **Keepa**：借鉴可追溯的历史价格与时间轴证据。
- **Helium 10 Black Box**：借鉴由简到繁的筛选、预设、字段解释与结果表。
- **卖家精灵**：借鉴“自定义市场样本 / 价格带 / 竞争集中度 / 季节性”的市场研究方法；不把它直接塞到组内分析页。

不是按某个百分比拼接这些产品的 UI。**商品组横向比较**是 V2 核心，新的成交指标只在数据可靠时加入；管理与采集页面的导航融合排在核心分析之后。

## 三、逐产品对标：具体页面和交互

### 3.1 店雷达：1688 行业字段与监控动作

直接证据：

- [竞店上新公开页面](https://www.dianleida.net/1688/competeShop/productAnalyze/addNewAnalyze/)：近 7/14/30 天、自定义日期、商品/类目关键词、查询/导出及列标题“所属店铺、价格、上架时间、月销件数、预估月销售额、总订单数、总收藏”等。页面标注**示例店铺数据**，不等于已验证具体交易数据或私有后台排序结果。
- [价格修改公开页面](https://www.dianleida.net/1688/competeShop/productAnalyze/priceModify/)：按时间与店铺显示价格变更，展示“原价格 / 新价格”，有具体 SKU 语境。
- [店铺销售分析](https://www.dianleida.net/1688/competeShop/salesAnalyze/salesData/)：销售件数、预估订单、预估销售额、动销率等**店铺级或预估指标**，不能直接拿来当 Offer 精确数据。
- [商品筛选页面](https://www.dianleida.net/1688/competeShop/goodsProductList/)：价、MOQ、销售/订单、上架时间和商品标识等筛选项。
- [店铺榜与列设置](https://www.dianleida.net/1688/competeShop/shopProductList/)：公开设置项包括月代发订单、收藏、评论、价格、库存、趋势等，证明其 UI 数据概念，但不证明项目自己可稳定采集这些字段。

**建议迁移**：公司名称/店铺作为表格首列；组内快捷筛选“最近有调价、MOQ 更低、近 7 天有上新、标签为严选/新品”（仅在数据真实可用时展示）；动作展示原值→新值、检测时间和来源商品。

**不迁移**：整店销售与单品销售混用、预估成交当真实成交、复制其商品库与会员体系。

### 3.2 Jungle Scout：最适合 Group Detail 的结构

官方 [Product Tracker](https://www.junglescout.com/features/product-tracker/) 和 [Group Options 帮助文档](https://support.junglescout.com/hc/en-us/articles/360008769073-Group-Options-on-Product-Tracker) 描述：同类商品分组、组级汇总、时间范围、Heatmap，并能跳到组内商品；[列配置帮助文档](https://support.junglescout.com/hc/en-us/articles/33653773303831-Customizing-Columns-on-Product-Tracker) 提供显示/隐藏列、调整顺序。

**建议迁移**：
1. 商品组是工作对象，主对比表是页面中心，而不是我方大卡片 + 抽象差距数字 + 事件排行。
2. 列按业务任务划分“商品竞争 / 经营表现 / 口碑履约”，第一版仅固定预设，无需拖拽定制平台。
3. 选择一列按可比较指标排序，**我方参与真实名次，不固定排第一**；另设持续可见的“我方第 X / N / 定位我方”。
4. 高亮可作为辅助，但不能在“库存更高=一定更强”“成交档位不可排序”等场景用热力色制造判断。

**不迁移**：Amazon BSR、Buy Box、平台销售预测。

### 3.3 Keepa：历史趋势与可追溯证据

[Keepa 官网](https://keepa.com/) 的明确主张是商品价格历史图及价格下跌提醒。公开资料不足以证明其登录后所有图表细节，本研究只借鉴其“历史证据有价值”的方法。

**建议迁移**：在公司/Offer 单品证据页通过图表标出真实价格点、最近事件发生时间、前值/后值；如果观察缺日，显示缺口，不填零；历史成交有可靠的连续观察后才展示成交趋势，不把 100+ 画成精确 100。

### 3.4 Helium 10：分层筛选与操作复杂度控制

[Helium 10 Black Box Product Tab 官方帮助](https://kb.helium10.com/hc/en-us/articles/6710274045339-Black-Box-Product-Tab-Overview) 确认：

- Simple / Advanced 模式；
- 按 Product、Competitors、Sales 分类的高级条件及字段 tooltip；
- 高增长/低评分等筛选预设和自定义预设；
- 结果表调整列；可选展示价格或销量等附加趋势细节。

**建议迁移**：默认只给“选择指标、排序方向、搜索公司、仅看近期变化、标签筛选”等高频操作。复杂条件以后收在二级抽屉或折叠区，避免组分析变成巨大的筛选配置页。不应让 Black Box 的销售估算或机会得分进入目前只有 8 个选定直接竞品的组内排名。

### 3.5 卖家精灵：市场研究必须和组内对标分离

[卖家精灵市场调研官方页面](https://www.sellersprite.com/cn/channel/market-research) 描述自定义市场分析样本、全年走势、竞争集中度和价格带。

**建议迁移**：后续创建一个独立“市场观察样本”的概念：固定关键词、时间、过滤条件、样本数和代表性说明；在此基础上分析新上架密度、成交/需求趋势、价格带及头部集中度，再加上我方真实利润空间。

**不迁移**：直接把人工挑选的 8 个竞品称为“全市场”；不能因某竞品销量高就判断 A19 所在细分市场有潜力。

## 四、Group Detail V2 信息架构草案（非冻结原型）

建议桌面从上到下仅保留四个主要区域：

~~~text

我方 1 + 直接竞品 8 | 真实采集时间 | 数据覆盖与来源提示

（如果口径不明，显示“暂无可确定排名”；不是全市场名次）

[商品竞争] [经营表现*] [口碑履约*]   搜索公司 | 标签 | 仅看变化

公司（主）/Offer（次）  价格  MOQ  SKU  最近变动  详情
~~~

*经营表现/口碑预设只有数据 POC 通过后才启用。以上价格和排名纯示意，不是 A19 的真实业务结论。*

### 4.1 信息优先级

- 公司名称为主，商品型号/Offer ID 为次，若真实企业主体不可得，则以真实店铺名回退；同公司多 Offer 仍分别成行，不合并/重复加总成交。
- 页面最显眼的不是“0/8”“2/8”，而是**当前选择的指标、我方在实际可比较样本中的位置、位于前面的公司**。
- KPI 数字可以作为表格快捷过滤（例如“2 家 MOQ 更低”点击后直接列出那两家），但不继续占首屏主要高度。
- 库存仍作真实事实，不用库存下降推断成交或爆款。
- 近期动态应能够直接定位某公司、时间、前值→后值、具体证据；不是用事件数多少充当竞争力评分。

### 4.2 排序/排名的不可突破的边界

1. **参与单位是 Offer，不是公司**；公司只是主视觉身份；同公司多个 Offer 不相加。将来如果需要公司级汇总，另做主体识别和可加性规则。
2. 我方参与排序；**不能为美观而固定到排名第一行**，可另设“定位我方”或顶部小型名次摘要。
3. “我方第 X / N”中的 N = **该指标同口径可比较的商品数**，不是组内总 Offer 数。无事实/不同比价规格/不同时间窗的商品可继续显示但不进入名次。
4. 相等值允许并列名次；缺失、不确定区间或数据过期时按 Spec 确定位置标记，不假装精确。
5. 类似 20+、100+、<10 应保留原文与上下界；**区间交叠时无法精确排序**。如只能判定部分前后次序，可写“可能名次区间”，前提是有经过测试的算法。
6. 商品链接最低价是 SKU 混放时的潜在引流价，不能冒充“同规格价格”。允许人工确认对标 SKU；两种价格口径要独立。
7. 店铺级好评率/揽收率与商品级评论、收藏不能混成一个商品竞争排名。
8. 平台新品/首发/严选/跨境等属于**平台或商品标签**，不能直接命名为平台分配的流量收益。

### 4.3 三个列预设

| 预设 | 指标列 | 接入前提 |
| --- | --- | --- |
| 商品竞争（先做） | 公司/Offer、可比价格或原始展示价、MOQ、SKU、库存、最近变化 | 已有 Snapshot；同规格可比性还须定义 |
| 经营表现（后做） | 公司/Offer、上架时间、月成交/月代销、年度成交、标签 | POC 验证口径、成功率与权限；只出现可用字段 |
| 口碑履约（后做） | 公司/Offer、评论、好评率、揽收率、收藏、指标归属 | POC 证明粒度与窗口，缺失不填 0 |

默认不做 15 列并排、不做 Excel 级别的自定义拖拽/保存布局。少量真实有效字段胜过全是“—”的豪华报表。

## 五、三条真实运营工作流（对标后的产品目标）

### A：我方在哪里？

1. 竞争总览选 A19。
2. 进入组分析，默认展示商品竞争列。
3. 切换价格/MOQ/SKU，看到“我方真实位置”和“前方有哪些公司”；缺可比性就明确显示原因。
4. 点公司对应 Offer 进入事实与 SKU 详情。

**验收**：约 10 秒内能找出我方价格/MOQ 位置及对应竞争公司，而非读完整表自己推导。

### B：最近哪个对手有动作？

1. 选近 7 天及“降价 / MOQ 降低 / SKU 调整”。
2. 展示公司、商品、实际前后值、时间与证据。
3. 如未来有相同口径连续成交观察，可显示事件与成交档位的时间关联，但不能说“降价导致销量上涨”。

**验收**：1 次明确降价不会被 10 次小库存波动的事件条数淹没。沿用既有 Group Attention 降噪能力，不另建风险评分。

### C：这个商品有没有市场机会？

1. 不能用精选 8 个竞品就回答全市场。
2. 后续独立取得关键词/市场样本与历史需求趋势。
3. 补我方真实采购成本、平台扣点、履约售后和利润。
4. 输出可解释事实、证据缺口和建议检查事项；未具备数据时显示“暂不能判定市场潜力”。

**验收**：不会依据库存下降或“新品”标签直接给爆款评级。

## 六、技术现实与研究缺口：已有销量 POC 必须复用

仓库现有 [1688 销量数据源验证](1688-sales-source-validation.md)（2026-09-20）：

- 5 个 active 商品中，3 个成功捕获采购助手相关响应，2 个未触发请求；
- last30DaysSales 出现 20+、<10 一类非精确显示；
- totalSales 和 totalOrder 可见但业务定义未确认；
- saleQuantityList 的日期记录稀疏，不能直接当每日销量序列；
- **没有字段达到 READY**，也没有正式接入 Collector/Schema。

因此下一步不是从零重做同样的 POC，而是**定向补充研究**：

- 未触发响应与成功响应的差异、重复访问的稳定性；
- 页面/官方说明确认“月成交”“月代销”“年成交件数”“年成交笔数”的具体粒度、单位、窗口；
- 商品/店铺企业主体名称、上架日期、评价/收藏、标签的真正数据来源；
- 原始页面 vs 扩展增强层、登录依赖、授权访问条件；
- 精确/区间/下界显示的存储和排名合同；
- 插件不可用时新指标不影响现有价格/SKU/库存采集。

**数据缺失不等于 0；未获得授权的接口不绕过访问条件。** 任何商业 SaaS 官方列出“月销件数”，都不代表项目捕获的 last30DaysSales 已与其统计口径相同。

## 七、借鉴哪些、不做哪些：效果与成本取舍

| 候选改造 | 业务收益 | 数据依赖 | 开发/维护 | 判断 |
| --- | --- | --- | --- | --- |
| 公司主标识 + Offer 次标识 | 高 | 已有店铺名；企业名来源待补 | 低～中 | **优先** |
| 现有价格/MOQ/SKU 指标排序 + 我方定位 | 高 | 已有快照；可比规格要定义 | 中 | **优先** |
| 简洁列预设 + 最近变化筛选 | 高 | 既有事实 | 低～中 | **优先** |
| 原价→新价 + 历史入口 | 高 | 已有 ChangeEvent | 低 | **优先复用** |
| 月/年成交排名 | 极高（若可靠） | POC 暂未 READY | 高 | **先补 POC** |
| 标签/上架日期/评价/收藏 | 中高 | 尚待来源验证 | 中 | **分字段试点** |
| 十几列拖拽自定义报表 | 中低（单用户小样本） | 低 | 高 | 暂缓 |
| 店铺级合并销量排名 | 易误导 | 主体识别/可加性缺口 | 高 | 暂不做 |
| 大量热力图与分数卡 | 低或易误导 | 可比性缺口 | 中 | 暂不做 |
| 导航合并全部旧页面 | 中 | 不依赖数据但回归大 | 中高 | **分析成功后再做** |
| 全市场爆品预测 | 高但不可信 | 市场样本、需求、利润均缺 | 很高 | **独立后期研究** |

## 八、建议实施顺序及验收 Gate

**优先保持两条互不阻塞路径：**

A. **已有事实位置**：明确价格可比口径 → 写最小 Group Position Spec → 实现“按公司展示/按指标排序/我方位置/证据跳转” → 用 A19 真实数据验收。

B. **经营指标增量 POC**：继承 9 月销量研究 → 逐字段标注 READY/PARTIAL/NO-GO → 仅对 READY 字段冻结采集与观察合同 → 加入经营表格预设。

两条路径可以并行研究，但每个业务 Feature 按项目协作方式小而完整地交付，不按 Backend/Frontend 机械拆分多次。

Group Detail V2 稳定使用后，再升级 Dashboard 摘要；最后才评估“我方商品 / 竞品列表 / 竞品分组”合并管理入口和采集记录弱化导航。市场机会分析单独研究，不能用组内排名代替。

### 六项人工验收题（A19 真数据）

1. 按 MOQ 排序后，我方在哪里？前面的公司是什么？
2. 同公司两条 Offer 会不会误合并成交？
