## 0. 执行摘要与最终取舍

### 0.1 新定位

不再以“采集多少竞品、监控多少字段”为主要产品目标，而以**我方商品为中心，形成可追溯、可比较、可解释的运营竞争情报**。

系统必须逐层回答：

1. **今天先看谁？** 哪些我方商品组的外部竞争发生了值得检查的变化？
2. **我方现在在哪里？** 对同一细分款式，我方在监控样本中的成交、价格、采购条件和口碑处于什么位置？
3. **对手做了什么、之后怎样？** 价格、MOQ、SKU、标签等变化的事实与后续公开表现如何？
4. **这个品是否值得继续投入？** 市场需求、竞争强度、生命周期和我方经营收益是否支持继续做（需要额外市场样本与经营数据）。

### 0.2 决策摘要

- **经营数据分两级 Gate。** Gate 1 验证页面展示值的合法来源、Offer 归属、自动读取可行性、稳定性与失败隔离，允许保留并展示原值；Gate 2 在统计口径、精度、时间窗口与可比性明确后，才开放精确排名、增长计算和综合评分。Gate 2 不阻塞 Gate 1 已通过字段的原值展示。
- **复用已完成的 Track A。** 我方组内竞争位置 V1 已实施；后续推进 Group Detail V2 的经营事实展示与分析，不重新规划 Track A 为待交付项。
- **不做假精确的爆品/废品结论。** `40+`、`<10`、`100%` 等可保留为原始展示值；原值展示、档位比较和精确排名是不同能力。组内排名不等于全市场排名；库存下降不等于销量；无充分口径时不计算精确增幅或综合评分。
- **不急着合并所有页面。** 稳定核心分析后，再把低频商品、竞品、分组管理入口合并；采集记录保留为排障能力，不强行塞进分析主屏。
- **不重写系统架构。** 继续 React/TypeScript、FastAPI/SQLAlchemy、Playwright/本机 Chrome、SQLite/Alembic 和唯一 Batch Runner；沿用 Snapshot、ChangeEvent、Attention、Group Detail 与 Detail 证据链。

### 0.3 正式优先级与并行依赖（统一口径）

```
现有 Track A / Group Detail V1 / Snapshot / ChangeEvent（已完成并复用）
    │
    └── Track B（经营数据两级 Gate）
           → Gate 1：页面原值采集与原值展示
           → Gate 2：满足统计口径后才作比较与派生分析
           → 逐步扩展 Group Detail V2
                         ↓
                竞争动态/真实趋势深化
                         ↓
             Dashboard 对接与低频导航收敛
                         ↓
            市场样本 + 我方利润 → 市场机会
```

**Track A 已完成并继续复用。** Gate 1 仅控制经营字段原值采集/展示的准入；Gate 2 仅控制这些字段参与比较和派生分析。Gate 2 不阻塞已通过 Gate 1 的原值展示，也不阻塞 Group Detail V2 的其他已具备事实能力。

## 1. 现状基线与问题诊断

### 1.1 已有可复用资产

以下是仓库当前可以复用的**已实现能力**，不是需要重新规划重做的任务：

- `Competitor`、`CompetitorGroup`，`ownership` 与 `group_role` 分离、我方商品绑定、竞品分组及生命周期；
- `ProductSnapshot`、`SkuSnapshot`、`CollectionRun`、`ChangeEvent`，含价格、MOQ、SKU、库存、标题/主图和历史变化；
- Playwright + 本机登录 Chrome 采集、既有失败/验证/风控恢复与 Batch Runner；
- Group-first Dashboard、Group Attention、Group Detail 只读聚合、Competitor Detail 证据页；
- React + Vitest、Playwright E2E、FastAPI pytest 与既有 Mock seam。

当前 `backend/app/collection/types.py` 的 `ProductData` 不含经营成交、评论、收藏、标签等指标。`backend/app/models.py` 的核心 Snapshot 亦无这类历史字段；现有 `Group Detail` 比较四个维度：价格、MOQ、SKU 数和完整库存。故**当前不存在可靠的销量排名数据来源**。

### 1.2 当前产品症结

| 症结 | 当前表现 | 真正影响 | 重构原则 |
| --- | --- | --- | --- |
| 以明细展示为主 | 大量商品标题、差异文本、事件数 | 用户仍需自己找“我方排第几” | 以公司主标识 + 统一表格 + 排序位置为主 |
| 差距计数不可定位 | `0/8`、`2/8` 等摘要 | 看不到是哪家、差多少 | 摘要能点击或筛出明确对象；主要以实际排序为准 |
| 无成交与口碑事实 | 只有价格/库存/SKU/MOQ 等 | 不能判断对手是否真的卖得好 | 新指标先 POC、后建模 |
| 标题识别成本高 | 商品标题长且相似 | 看表时不容易识别供货商 | 公司名主显示、型号/商品副显示 |
| 变化与表现断裂 | 事件有记录，缺可比结果 | 不知道动作后的公开表现 | 历史观察对齐，禁止直接推断因果 |
| 页面入口过多 | 自有商品/竞品/组/采集任务并列 | 日常高频路径被低频管理打断 | 先稳定核心分析、后融合管理入口 |
| 组内样本被误读为市场 | 仅选择 8 个对标商品 | 易产生“全市场第几”的错觉 | 明确区分“组内样本”和“市场观察样本” |

### 1.3 成功标准不再是功能数量

真正的最小目标：以真实 A19 商品组测试，用户打开页面 **5～10 秒内**能够找到我方在一个指定指标下的可解释位置，识别具体领先/落后对手，并能验证数据来源；最近变化能够指向具体公司/商品/时间及证据。此为人工体验目标，不保证所有指标都有可排名数据。

## 2. 核心业务对象和边界

### 2.1 必须区分的五种身份/粒度

1. **商品组（Group）**：我方一种明确型号/对标意图，例如 A19 磁吸暖手宝；不是 1688 全市场。
2. **商品链接（Offer）**：当前主要业务/采集唯一对象，以平台 + Offer ID 识别，可能包含多个 SKU。
3. **SKU/对标规格**：价格与功能可比性的最小单元，尤其要识别引流低配 SKU 与我方主销 SKU。
4. **店铺/企业主体**：公司名称、店铺名称、商家身份可能不同；主视觉可以显示公司名，但不能拿公司名代替 Offer 唯一标识。
5. **市场观察样本**：后续依据固定关键词、筛选条件与采样时间形成的集合；与人工精选直接竞品组分开。

### 2.2 公司名称优先展示，不等于按公司聚合成交

建议 Group V2 一行对应一个实际 Offer，主标题显示**有来源且可验证的公司名称**，次标题显示型号、缩短后的商品名、店铺名或 Offer ID；我方行突出标识。

- 公司名称缺失时退化为真实店铺名称；仍无时显示 Offer ID，并明确“公司未确认”。
- 同一公司出现多个链接时，行可以同名并辅以商品标识，不自动合并、去重或累加销量。
- 未来如确需公司级汇总，须单独建立企业主体识别、去重与指标可加性规则。
- 店铺级揽收率/服务评分须明确标记“店铺指标”，不可伪装为该 Offer 的单品表现。

### 2.3 可比性是排名的前置条件

同一链接内不同容量、包装、型号、认证、零售/批发条件、MOQ、运费或促销可影响实际价格。默认展示原始价格事实，但不将“各链接最低引流价”称为“同规格价格排名”。

首期无需等待自动 SKU 匹配：可以先对**链接展示价/报价下限**做明确标注口径的事实排序，也可直接对已可比较的 MOQ、SKU 数进行组内位置分析；但**不得把链接展示价排序宣传成同规格价格名次**。只有经过人工确认的对标 SKU 才能进入“同规格价格位置”，其最小确认方式和保存边界留待首期正式 Spec 冻结。

## 3. 新增经营指标清单与来源状态

> 本表是候选采集目录，**不是已经确认可用的数据合同**。字段中文名以用户需求为起点，语义待 POC 核对实际页面/插件口径。

| 字段 | 暂定对象/粒度 | 优先级 | 必须核对的口径或风险 | 现有 POC 观察状态 | 当前产品化决策 | 后续 Gate |
| --- | --- | --- | --- | --- | --- | --- |
| 公司名称 | 商家/企业 | P0 | 公司主体、店铺展示名是否一致 | 不属于十类经营指标 | Hold，另核来源与 fallback | 身份字段验证 |
| 上架时间 | Offer | P0 | 首次上架还是最近重上架、显示日期精度 | No-Go（未观察） | Hold | Gate 1 原值；Gate 2 比较 |
| 月成交 | Offer 或店铺待核对 | P0 | 单位、统计主体与窗口；`40+`、`<10` 等不是精确值 | Partial（观察到档位值） | Hold | Gate 1 原值；Gate 2 比较 |
| 月代销 | 待确认 | P0 候选 | “代销”含义、是否独立指标、是否对应真实成交 | Unverified | Hold | Gate 1 原值；Gate 2 比较 |
| 年成交件数 | Offer 待核对 | P0 | 年度窗口、成交数量还是商品件数 | Unverified | Hold | Gate 1 原值；Gate 2 比较 |
| 年成交笔数 | Offer 待核对 | P0 | 订单笔数 ≠ 商品件数，年度口径 | Unverified | Hold | Gate 1 原值；Gate 2 比较 |
| 评论数 | Offer 或店铺待核对 | P1 | 评价与成交关系、是否去重/累计 | Unverified | Hold | Gate 1 原值；Gate 2 比较 |
| 好评率 | 商品或店铺 | P1 | 分母、窗口、精度、无评论时的空值 | Unverified | Hold | Gate 1 原值；Gate 2 比较 |
| 揽收率 | 多为商家/物流维度，待核对 | P1 | 48h、24h 等窗口与指标含义必须保留 | Unverified | Hold | Gate 1 原值；Gate 2 比较 |
| 收藏数 | Offer | P1 | 实际收藏统计还是界面交互展示值 | Unverified | Hold | Gate 1 原值；Gate 2 比较 |
| 平台标签 | Offer/SKU/活动待核对 | P1 | 精确识别、新旧状态、来源与粒度 | No-Go（未观察） | Hold | Gate 1 原值；Gate 2 比较须有定义 |
| 价格/MOQ/SKU/库存 | 当前 Offer/SKU | 已有 | SKU 混放、完整库存 vs 未知库存 | 不适用 | 直接复用 | 现有能力 |

特殊规则：

- “新品/严选/跨境”等先称**商品/平台标签**，不能由标签名称推断流量奖励、真实曝光或销量。
- Gate 1 完整 POC 范围为十类：**上架时间、月成交、月代销、年成交件数、年成交笔数、评论数、好评率、揽收率、收藏数、平台标签**。公司名称是身份字段，不计入这十类经营指标。
- 平台标签候选完整列为：**新品、人气新品、首发新品、超级新品、严选、跨境、镇店之宝、哇偶定制**。精确识别标签，不通过子串推断其他标签；分别记录“未出现”与“未成功采集”。
- Gate 1 可保留 `40+`、`<10`、`100%` 等页面原始展示值，不强转为精确数值；区分原值展示、档位比较和精确排名。
- 数字需区分**精确值、下界值、上界值、区间值、缺失**，同时保留页面原文、单位、观察时刻与来源。不同统计窗口或主体不可直接比较。
- 日期、百分比与成交口径必须记录“商品级/店铺级”、统计窗口和来源。不同窗口或不同统计主体不能直接横向排名。
- SKU 库存变化不能作为月成交/销量的替代数据。

## 4. Track B：新增经营指标的增量 POC（仅新数据的前置 Gate）

### 4.1 两级 Gate 与已有研究状态

**先复用** [2026-09-20 的 1688 销量数据源验证](../research/1688-sales-source-validation.md)：既有 5 个 active Offer 样本中，3 个捕获采购助手相关响应、2 个未触发；`last30DaysSales` 为 `20+`、`<10` 等不精确字符串，`totalSales` / `totalOrder` 口径不明，**目前没有任何成交字段达到 READY**。不重新做一份相同的“从零验证”。

现有 [经营指标增量 POC](../research/1688-performance-metrics-poc.md) 只记录了月成交、上架时间、平台标签三类的既有证据：月成交为 Partial，上架时间和平台标签为 No-Go。其余七类尚未观察。No-Go 表示当前没有足够证据进入产品化，不代表技术不可行；既有 POC 未做重复观察，也没有验证新增来源或访问授权，本计划不把产品目标变化写成已完成的技术验证。

后续 Gate 1 POC 覆盖本节列明的十类字段，验证合法来源、Offer 归属、自动读取可行性、稳定性及失败隔离，并按字段记录页面原始值、来源、观察时间和已知粒度。Gate 1 不要求精确数值或完整统计口径；通过字段可按原值展示。

Gate 2 独立判断统计口径、精度、时间窗口及跨 Offer 可比性是否足以支持**精确排名、增长计算或综合评分**。Gate 2 未通过时仍可展示已通过 Gate 1 的原值。两级 Gate 均不阻塞已完成的 Track A，也不允许经营字段失败影响现有价格、库存、MOQ、SKU 采集。

### 4.2 对象与次数（建议基线，可根据实际候选调整）

- 在既有 5 个样本与失败记录基础上，建议扩展到 **1～2 个我方 Offer + 8～12 个不同公司/不同展示形态的竞品 Offer**；优先覆盖先前 2 个未触发请求的场景，而不是丢弃旧证据重测；
- 样本覆盖十类字段中的可见、不可见、档位值和失败场景；标签样本覆盖新品、人气新品、首发新品、超级新品、严选、跨境、镇店之宝、哇偶定制及未出现标签；同时涵盖不同上架时间、评价、缺失数据、多 SKU 混放、下架/加载异常；
- 至少在两个不同时间点进行采集（优先相隔 24 小时），加一次重复加载观察 DOM 稳定性；技术 POC 样本小，不把成功率当作全平台统计结论；
- 对同一 Offer 记录“1688 原生页面”与“浏览器插件增强区”之间的来源归属，不默认插件可被服务端持久采集。

### 4.3 必须验证的技术问题

1. 页面显示值究竟来自官方原生 HTML、内嵌 JSON、页面可见 DOM、XHR/Network 还是浏览器扩展？
2. 当前项目所用的独立 Chrome Profile 是否真的加载对应扩展？扩展 UI 在自动采集过程是否存在、是否依赖授权或额外登录？
3. 同一字段跨商品/跨访问时的结构稳定性如何？是否存在延迟渲染、不同页面模板、分页、接口权限等问题？
4. 这些数据允许如何访问和使用？核对平台/扩展的访问条件、许可及自动化限制；不得绕过登录、验证码、风控或调用未经授权的私有接口。
5. 对 Gate 1，能否保留页面值及来源、观察时间和已知粒度；对 Gate 2，“月成交/年成交/月代销”等统计对象、时间窗口、单位、精度与可比性是否能确定？
6. 是否可获得真正历史值，或只能按日记录抓取当时屏幕值？首次采集之前不存在可追溯历史。
7. 任一新字段抓取失败、页面验证或扩展缺席时，当前基础采集是否还能成功且原事实不被污染？

### 4.4 POC 输出表与可复核证据

逐字段记录：`中文字段 | 原始显示 | 数据来源(原生/插件/网络/未知) | Offer归属证据 | 已知粒度 | 观察时间 | Observed/Partial/Unverified/No-Go | 产品化 Hold/Go | Gate 1 自动读取/稳定性/失败隔离证据 | Gate 2 口径/精度/窗口/可比性 | 风险`。观察状态与产品化决策分开记录；未观察到字段标 Unverified，不能由此推断技术不可行。产品化 Hold/Go 分别说明是否准入原值展示，Gate 2 另记比较/派生是否准入。

另附：脱敏的最小页面证据（局部截图/可安全保留的片段）、样本清单（Offer ID 可代号化）、成功/失败原因、允许的访问方式说明。绝不提交 Cookie、Token、完整登录 Profile、私有请求密钥或含账号隐私的原始日志。

研究报告路径：`docs/research/1688-performance-metrics-poc.md`（本地文件已存在；其现有证据保持不变）。

### 4.5 Go / Partial / No-Go（拟议决策门槛）

- **Gate 1 Go**：单字段来源合法、Offer 归属可确认、自动读取可行且稳定，失败可隔离；保留原始值、来源、观察时间和已知粒度即可，不要求完整统计口径或精确数值。
- **Gate 1 Partial/Hold**：证据不完整或字段读取不稳定，暂不产品化该字段；记录已观察事实和缺口，未观察到字段保持 Unverified，不等于技术不可行。
- **Gate 1 No-Go/Hold**：当前来源或访问方式不合法、不可自动读取或无法隔离失败时，不准入该字段；不得影响现有价格、库存、MOQ、SKU 采集。
- **Gate 2 Go**：只有统计口径、精度、时间窗口及可比性充分明确后，才准入对应的精确排名、增长计算或综合评分；按分析类型分别说明证据。
- Gate 2 Hold 只暂停比较和派生分析，不撤销 Gate 1 已准入的原值展示。

任何 Gate 失败都不阻断已完成的 Track A；未经相应 Gate 和正式 Spec 评审，不预建生产 Schema 或排名合同。

## 5. 数据与技术演进原则（待各阶段 Spec 定义）

### 5.1 目标数据通路（概念图）

```
现有采集入口 / 唯一 Batch Runner
     ├── 既有 ProductData → ProductSnapshot + SkuSnapshot → ChangeEvent
     └── Gate 1 通过的页面原值采集适配
                 ↓
        原值 Observation（来源/观察时间/已知粒度）
                 ↓
          原值展示（不要求精确口径）
                 ↓
      Gate 2 通过的比较与派生分析
                 ↓
             Group Detail V2
                 ↓
        Dashboard 摘要及单 Offer 证据
```

- 新增经营观察数据与现有快照可用**独立逻辑边界**保存，避免一次失败导致现有采集失败；是否独立建表、是否采用 JSON 或 typed columns，由 POC 后的正式 Spec 和 migration 评审决定。
- 保留每次有效观察的时间与来源；失败/缺失不覆盖最近一次有效事实，也不制造“全 null 的假快照”。
- 使用已有 Runner / session / 锁与错误状态；不新增第二个采集调度器或跨进程队列。
- 不把扩展/第三方页面结构写死到 Group Detail API；原始读取与标准化需隔离，尽量保持一个字段变更只影响采集适配与验证。
- 若采集频率不同，数据在页面显示各自的采集时间；不要把“价格刚更新，成交昨晚更新”伪装为同一时刻。
- 不引入 Redis、Celery、微服务、外部 SaaS 必选依赖或新前端状态框架。

### 5.2 经营观察字段必须保留的元信息

Gate 1 最低语义：`platform + offer_id/subject_id、metric_key、raw_display、known_subject_scope、observed_at、source、quality_status`。Gate 2 若获准计算，再补足并校验精度、单位、统计窗口、边界及可比性所需定义。

此为**概念性校验清单**而非冻结数据库表。Gate 2 进行比较或派生计算时，数值上下界须明确端点是否开闭（例如 `100+` 不应当作 `[100,100]`），并确认时区与统计窗口；Gate 1 原值展示不以此为准入条件。

### 5.3 前后端职责

- Backend 权威生成 Gate 2 已准入的排名、比较资格、派生指标、数据状态、聚合、事件摘要及稳定排序；Gate 1 值可按原文展示，不暗示可比较。
- Frontend 展示筛选/排序状态、公司身份、我方位置、来源提示、Loading/Partial/Error，提供证据跳转。
- 不因为筛选引起的排名口径变动让用户误以为“全组排名”。默认排名以**完整合格对标组**为分母；筛选结果排名如要展示，必须明确标为“当前筛选内”。

## 6. Group Detail V2：核心业务页面

### 6.1 页面职责

回答“我方在这个**可比商品组**的位置是什么、谁有优势、最近什么在变、哪些结论值得核查”，不是重新做竞品管理、整合全部单品详情或市场选品 BI。

建议结构：

```
Header：A19 磁吸暖手宝 / 数据更新时间 / 样本口径
我方位置摘要：选择指标 → 组内名次/并列/未知 + 对标样本范围
主对比表：公司为主、商品为次、我方高亮，筛选/排序/列预设
近期值得查看的竞争变化：公司 + 事件事实 + 时间 + 证据
历史观察：真实可得的价格/成交/标签记录（分阶段启用；经营指标先呈现原值，比较趋势须 Gate 2 通过）
```

拒绝为填充空间引入大量无依据的 KPI。原 `0/8` 类计数可降为表格快捷筛选提示，不再作为首屏的主要分析表达。

### 6.2 主要组件与交互

1. **商品组与基准**：组名、我方链接/身份、直接竞品数、真实数据可用数、最新采集时间。不是全市场样本。
2. **排名指标选择**：复用已有 Track A 的 MOQ、SKU 数及明确标注口径的链接展示价能力；同规格价格位置只有在人工确认 SKU 后才可作为确定名次。Gate 1 通过的经营字段可显示原值；只有 Gate 2 通过的字段才可用于精确排名、增长计算或综合评分。
3. **组内对比表**：我方参与已获准的排序且仍突出；主标识公司名称，次行显示 Offer/产品信息。标题很长时截断、悬停/详情可查看。仅对已确认可比较的指标提供排序；搜索公司、标签过滤、条件过滤。
4. **字段预设**（先轻量，无复杂自定义报表框架）：
   - 经营表现：公司、上架时间、月成交/月代销、年度交易、标签、变化；仅展示已通过 Gate 1 的字段，比较和派生分析另须 Gate 2 通过；
   - 商品竞争：公司、对标 SKU 价格、原始链接价格、MOQ、SKU、库存、变化；
   - 口碑履约：公司、评论、好评率、揽收率、收藏、数据归属；
   不通过 Gate 1 的字段不加入展示；Gate 2 未通过的字段只展示原值，不用于排名/增长/评分。
5. **我方定位**：排序后我方行保持真实名次（不通过把我方行固定第一伪造名次）；另提供置顶悬浮的我方摘要或“跳转到我方行”便于寻找。
6. **变化证据**：竞争动态优先显示明确降价、MOQ 降低、SKU 上新/下架、已确认标签出现/消失等事实；标签未成功采集不得解释成未出现或已消失。库存微动继续降噪；动作数量不得等同竞争威胁分数。
7. **历史视图**：只展示已有真实 observation；经营指标先呈现原值和观察时间，比较趋势须 Gate 2 通过。可叠加事件标记，但不声称价格变化导致成交变化。
8. **提示与状态**：加载、无对标商品、未绑定我方、数据部分缺失、公司名称未知、数据过期、停止监控、下架、排序不确定、访问失败均需明确。
9. **不重复建设**：单商品明细仍通过 Competitor Detail 查看；组/商品的增删改、绑定仍保留既有业务入口。

### 6.3 组内排名/筛选的业务合同候选

- 参与集合：我方一个已绑定 Offer + 本组当前直接竞品 Offer；仅字段同口径可比较者进入该指标分母。停止监控/下架商品是否列入“当前排名”，正式 Spec 必须定义并显式标注。
- 排名单位默认**商品 Offer**，公司是显示身份，不把同公司多个 Offer 自动按企业合并。
- 精确值允许并列排名并稳定展示并列者；不可比较和缺失列于末尾且不赋假名次。
- 原值展示不代表可比较。档位比较只有定义明确且比较规则获准后才启用；精确排名、增长计算或综合评分须 Gate 2 通过。区间重叠时不得按下限做精确排序。
- 百分比可按 Gate 1 原样显示（如 `100%`）；Gate 2 比较时必须确认同一商品/店铺粒度、分母及统计窗口，没有完整定义时不显示“更好”。
- 同规格价格位置与链接最低价排序是两列/两口径；绝不混用。
- 交易件数、交易笔数、代销量不可互换，也不按标签推测流量。
- 筛选/排序的条件、方向和有效样本数必须可见；可用公司/标签/近期变化/仅有数据等筛选；列数有限，避免横向溢出。
- “市场第 X”只能在另建具有明确抽样方法的市场观察样本后讨论；当前最多称“**组内第 X / N**”。

### 6.4 V2 对比表的明确验收案例

用 A19 真实或脱敏样本核对：

- 我方 + 8 个直接竞品；按价格升序后我方仍能定位，前方是什么公司一目了然；
- 两个 Offer 同公司但不同 SKU，不误合并为一家交易总量；
- `40+`、`<10`、`100%` 等原值可按页面原样展示；原值展示不生成档位比较或精确名次，精确排名只在 Gate 2 通过后出现；
- 部分商品评价缺失时明示缺失；只有 Gate 2 通过后才按有效样本计算比较/排名分母；
- 同一链接中的 4 个混合 SKU 不按最低引流价格冒充同规格市场价格；
- 八类平台标签按完整名称精确识别；未出现与未成功采集分开显示，短暂失败不生成“标签消失”事件；
- 单条公司行可直接打开来源商品/已有证据页面。

## 7. 竞争动态：从事件流水变成运营问题

### 7.1 三层信号

**事实层**：最新价格、历史快照、MOQ、SKU、真实成交观察、平台标签和 ChangeEvent。

**解释层**：同一商品/相近时间的事件可组合为“集中修改了价格与 SKU”这样的**事实聚合**；不得直接断言抢市场、清库存或价格战。

**行动检查层**：优先提供“建议核对同规格价格、是否促销、是否真实动销变化”，不自动给出降价价位或执行动作。

### 7.2 变化与结果必须分开

假如 10 月 3 日竞品价格从 ¥39 降至 ¥35，两个时点的页面月成交原值分别显示 `100+` 与 `200+`：

Gate 1 可分别展示两个时点的原值和观察时间；只有 Gate 2 的统计窗口及档位比较规则通过后，才可说“观察到月成交档位上升”。

不能说：“降价使销量翻倍”；档位不是精确销量，时间先后不是因果。

首阶段维持现有 Attention 去噪。后续新增交易/标签事件时单独定义可靠的变化检测规则，禁止让同一次采集刷新产生海量事件噪音。

## 8. Dashboard、管理页与导航重构

### 8.1 保持高频两层

- **竞争总览（现 Dashboard）**：今天哪些我方组值得看、为何、采集是否正常；不展开全部 Offer。
- **竞争分析（Group Detail V2）**：某个商品组内的排名、公司对比、最近动作与事实趋势。组选择可以在总览入口完成；是否新增独立“竞争分析”导航入口，以真实使用反馈决定。
- **单品证据（Competitor Detail）**：详细 Snapshot、SKU、ChangeEvent、采集记录与真实网页。
- **监控管理（低频）**：我方商品、竞品和分组合为**统一管理入口的多个子视图**，不是一个巨型页面。
- **采集任务/记录**：保留底层功能，通过采集状态/设置中的次级入口进入；出错时可快速找回。

### 8.2 禁止“一次重构全局页面”

必须先证明 Group Detail V2 和新数据已带来可用价值，再调整导航。

管理页面融合的预设顺序：统一入口与导航 → 原页面嵌入/分 Tab → 保持原 API 与保存语义 → 观察真实工作流 → 再考虑移除旧入口。不得同时重写业务状态、表单契约和路由。

## 9. 市场机会判断不是组内排名的简单延长

目标问题“潜力品 / 普通品 / 不值得继续做 / 爆品”是**市场层问题**，不能从自选的 8 个竞品推导。未来至少需要：

| 维度 | 最小事实输入 | 关键局限 |
| --- | --- | --- |
| 需求趋势 | 关键词搜索/行业趋势或合规可得的覆盖更广成交样本、季节曲线 | 单一 Offer 月成交不代表全市场需求 |
| 市场供给/竞争 | 固定查询条件下的供给样本、价格带、上新密度、头部集中度 | 需要注明采样方法、数量与偏差 |
| 商品生命周期 | 上架时间、真实成交趋势、标签变化 | 新品标签不等于自然流量/爆款 |
| 运营可行性 | 我方采购成本、税费、平台扣点、履约费用、售后和毛利 | 卖得动不代表做得赚钱 |
| 可控动作 | 规格差异、MOQ、报价、页面、投放/运营动作 | 不等于自动降价就能解决 |

未来建议创建“市场观察组”与“直接对标组”两个概念。市场观察组由固定关键词/筛选/采样时间组成，需声明覆盖和代表性局限；不得把自己的手动精选竞品说成全市场。

第一阶段不输出“爆品/废品”黑盒评级。输出带证据的机会判断：`需求迹象 / 竞争程度 / 利润空间 / 证据缺口 / 建议核查`；资料不足就显示“暂无法判断市场潜力”。

AI 仅在可靠事实、外部样本和经营收益完整后承担解释与文字总结，不负责凭空估销量、预测销量或替代运营决策。

> 下述阶段是产品规划，不是可直接执行的开发任务。每一阶段开始前依据真实代码与最新 POC 写独立 Spec；验收通过再进入下一阶段。工作量按相对范围分类，不承诺工期。

| **D. Gate 2 比较与派生分析 / Group Detail V2** | 对应字段统计口径、精度、时间窗口及可比性明确；Gate 1 原值可分批接入 | 仅对 Gate 2 Go 字段提供精确排名、增长计算或综合评分 | 不可比较值仍可显示原值；不产生假名次或假增长 | M |
| **E. 经营趋势与变化** | 真实观察积累一段时间；派生结论满足 Gate 2 | 观察对齐、事实趋势与事件证据 | 未过 Gate 2 时只呈现原值/已观察事实，不作增长推断 | M |
| **F. Dashboard 收敛** | Group Detail V2 稳定并有真实使用反馈 | 今日优先关注的组与组内关键变动衔接 | 总览入口能快速进入组分析；异常不被掩盖 | S～M |
| **G. 管理导航简化** | 高频分析路径稳定 | 统一监控管理入口，采集排障入口降级 | 原流程无失能、无大规模状态回归 | M |
| **H. 市场机会验证** | 市场样本 + 经营成本/收益；相关经营分析满足 Gate 2 | 需求/竞争/利润三维分析 POC | 区分样本与全市场，无法判断时不编造结论 | M～L |

### 10.1 第一批独立交付建议

- **Track A 已完成**：`docs/specs/group-competitive-position-v1.md` 已实施；后续复用，不重新创建首期 Spec 或重复交付已有位置能力。
- **现有 Research**：`docs/research/1688-performance-metrics-poc.md` 已存在且仅记录三类字段的既有证据；不把它描述为十类 Gate 1 验证已完成。后续按本计划补足 POC 证据。
- **后续经营指标 Feature Spec**：仅为 Gate 1 Go 的字段定义原值观察、采集、存储、降级和展示；精确排名/增长/评分另受 Gate 2 约束。必要时再写 Group Detail V2 扩展 Spec。
- 后续 Dashboard、管理融合、市场机会分别再写 Spec；**不要一次把所有范围冻结成一个超大 Feature**。

文件名仅为建议；实际创建前检查仓库状态。以一个完整业务价值闭环为单位交付，避免按 Backend、Frontend 或重复页面定义机械拆分。

### 10.2 优先级与机会成本

Track A 已完成；当前继续复用。
当前后续：Gate 1 十类字段原值 POC 与 Group Detail V2 规划并行；Gate 1 通过后可接入/展示原值，Gate 2 通过后才增加比较与派生分析。
较后：经营趋势、Dashboard 摘要、页面融合，保持 Group Detail V2 → Dashboard → 导航重构的顺序。
最后：市场机会、运营动作记录、AI 建议。

应暂缓：新组件库、重做全局 UI System、重构 App 路由、自动 SKU 语义匹配、公司级成交汇总、微服务/Redis、所有字段一口气入库、多平台/多用户、自动改价和黑盒爆品评分。

## 11. 测试、数据安全、验收与回滚

### 11.1 POC/采集验收

- Gate 1 对十类字段逐项使用有限、真实可复核样本，记录原值、来源、观察时间、已知粒度及 Observed / Partial / Unverified / No-Go；产品化 Hold/Go 独立记录；
- 登录/验证/下架/网络失败不删除最近成功事实；任一新增字段读取失败不使现有价格、库存、MOQ、SKU 采集失败；
- 两次重复观察同一数值不能生成虚假的成交增长；标签精确匹配列明的八类名称，不通过子串推断，未出现与未成功采集分开记录；
- Gate 1 原值展示不依赖精确统计口径；Gate 2 未通过时不做精确排名、增长计算或综合评分，但不隐藏已准入原值；
- 不强绕过页面风控、扩展许可或对外接口权限；浏览器 Profile/凭据仅留本机，不提交仓库；
- POC 脚本不得修改真实工作数据库，必要测试使用脱敏/临时环境和受控 mock。

### 11.2 Backend 验收

- 原值展示保留 `40+`、`<10`、`100%` 等页面字符串；转换/精确比较仅按 Gate 2 已确认的定义；
- 数据粒度：商品级 vs 店铺级、月 vs 年、件数 vs 笔数严格隔离；
- Gate 2 排名/派生：并列、重叠区间、缺失、离线/暂停、同公司多 Offer、同规格可比性；Gate 1 展示值不得暗示名次；
- 历史：失败保留旧值、来源/时间不丢、版本兼容、Schema 迁移回退路径；
- 聚合：同一 Group 的直接成员与 own 不重复计数，避免按商品 N+1 查询；
- 使用 pytest + TestClient + 临时 SQLite，确保无真实平台写入。

### 11.3 Frontend/UX 验收

- 公司名为主、Offer 为次，名称很长不会吞掉关键数值；
- 排序后的真实位置、我方定位、样本数、数据不足、区间不确定、并列、数据新鲜度清楚；
- 常用标签/指标筛选正确，切换指标不会把旧排名保留为新排名；
- 进入竞品证据/返回组分析正常；Loading、Error、Partial、Empty 完整；
- 桌面优先，窄屏能横向滚动或调整列，不遮挡操作；
- Vitest 保护排名展示契约与交互，Playwright 复用既有 API mock/导航 seam，人工以真实组检查使用成本。

### 11.4 回归与回滚策略

- 每阶段只做受控增量迁移与局部页面修改，原已有字段、历史快照、采集运行状态和 Dashboard 不应被新指标污染；
- 在开展任何 migration 前验证工作数据库备份、升级和回退/恢复策略；未经用户明确确认不操作真实 SQLite 数据；
- 新观察功能出现问题时可以关闭/停止新增采集，现有 Snapshot、ChangeEvent 和 Attention 继续可用；
- 不做批量删除旧页面/旧 API 的“一刀切迁移”，先保留低频入口，验收后才收敛导航；
- 禁止以“测试通过”替代对真实电商业务口径的人工核验。

## 12. 核心风险登记

| 风险 | 严重性 | 处理策略 |
| --- | --- | --- |
| 关键成交数据只在第三方插件 UI 可见，自动读取受限 | 高 | POC 判断权限/依赖；不绕过限制；允许 Partial/No-Go |
| 字段含义不明（尤其月代销、年件数/笔数） | 高 | 原文 + 来源 + 窗口；未验证不参与排名 |
| `100+` 等档位造成虚假精确排名 | 高 | 区间/上界/下界类型、保守排序、明确“无法精确排名” |
| 同一 Offer 多规格混放，低价 SKU 误导运营 | 高 | 人工对标规格；分开原始价格和同规格价格 |
| 店铺指标被当成商品指标 | 高 | subject_scope 强约束；UI 显示口径 |
| 登录态/验证/扩展依赖导致采集不稳定 | 高 | 可观察错误、失败隔离、沿用现有安全的采集限制 |
| 先大改导航，核心分析功能仍然不强 | 中高 | 导航融合放最后，保留低频后台能力 |
| 以 8 个竞品推断整个市场机会 | 高 | 另建抽样、需求趋势与成本数据，保持判断缺口 |
| Schema 迁移污染历史事实 | 高 | 单独 Spec、临时数据库测试、备份与可回退策略 |
| 形成复杂 UI/技术栈，维护成本增长 | 中 | 每阶段小而完整，复用现有代码和测试，拒绝提前抽象 |

## 13. 产品验收脚本：用 A19 检查是否“真的有用”

### 每日例行（3 分钟内完成核心检查的目标）

1. 打开**竞争总览**，看到 A19 及其他商品组的优先关注顺序和事实原因。
2. 进入 **A19 组内竞争分析**，选择“商品竞争/价格”指标。
3. 看到“我方可比较价格在 N 个合格商品中的位置”；按价格排序，识别价格低于我方的**公司**和具体 Offer。
4. 切到“经营表现/月成交”：Gate 1 通过即可看到页面原值及来源/时间/已知粒度；只有 Gate 2 通过时才看到可解释的比较或排名。`40+`、`<10`、`100%` 等不被强转为精确值。
5. 筛选近 7 天有变化的公司，看到其价格、SKU、MOQ 或已验证标签/经营原值的观察时间；标签未成功采集不能记作消失。
6. 打开单 Offer 证据，核对对标 SKU、具体字段和来源；决定是否需要人工跟进。
7. 对于“这个品是否值得继续做”，在尚无市场与利润数据的阶段明确展示“只能评价组内竞争位置，不能评价整体市场潜力”。

### 不通过的情况

- 打开组页第一眼仍只有 `0/8` 等抽象数字、找不到具体公司；
- 我方行无法在排序结果中定位，或所谓“名次”来自过滤后的隐含样本；
- 仅有档位/原始展示值却算出精确增长率、精确排名或综合评分；
- 同款不同规格和店铺级数据冒充商品级数据并混到一个名次；
- 新指标失败让原有竞品监控与采集不可用；
- 为整合导航牺牲了采集故障排查或商品管理能力；
- 没有市场样本却输出“爆品/废品”结论。

## 14. 项目协作、决策 Gate 与变更机制

严格遵守 `docs/roadmap/vibe coding协作方式.md`：

1. 本文为**规划提案**。用户确认产品方向后，遇到与旧 roadmap 冲突之处先明确调整产品规划，不将本文自动视为已冻结的 Feature Spec。
2. 经营数据分 Gate 1 页面原值采集/展示与 Gate 2 比较/派生分析；Research/POC 在 `docs/research/` 按字段记录 Observed / Partial / Unverified / No-Go 及产品化 Hold/Go。未观察到不等于技术不可行。
3. 每个涉及数据模型、筛选排名口径、页面组合的 Feature 单独整理 `docs/specs/`，Codex 自检、仅提交纯 Spec，ChatGPT 从 GitHub 独立 Spec Review，再 Freeze。
4. Implement 只执行冻结 Spec，targeted/full tests + 必要 Playwright QA，用户按风险完成业务/视觉验收；独立 Standards/Spec Code Review，P0/P1/P2 清零后才能提交业务代码。
5. **本规划文档提交不意味着任何 POC、迁移、页面重构或新采集功能已获得实现授权。**
6. 每阶段重新核对远端 `main` 和本地工作区。之前的历史 Spec 可能保留“当时尚未实现”的状态描述，应以最新代码和提交事实判断现状，不能机械地重新实现。

### 建议首先确认的产品问题

- 排名是以 **Offer 为单位，公司名为主标识**，不是直接按公司汇总成交——建议确认此定义。
- 价格比较以**人工确认的可比 SKU**为正式竞争位置，原始链接最低价另列——建议确认。
- 上架、成交和口碑等字段 Gate 1 通过后可先保留/展示原值；只有 Gate 2 通过后才参与精确排名、增长计算或综合评分。
- 是否同意“高频主入口两类：竞争总览 + 组内分析；低频管理后置融合”。
- 是否同意“市场潜力”单独作为后续阶段而非与组内分析同一批上线。

### 推荐启动任务

**Track A《我方组内竞争位置 V1》已实施，直接复用。** 后续按 Gate 1 对十类经营字段补充原值采集证据；Gate 1 不要求精确口径，Gate 2 再判断比较与派生分析。已存在的三字段 POC 结论保持原样，不能视作十类验证完成；任一新字段 Gate 失败不影响既有基础采集。

本文的价值是设定**先后顺序、范围边界和可否进入下一阶段的标准**，不是提前锁定全部细节，也不是以页面数量替代真实运营成果。
