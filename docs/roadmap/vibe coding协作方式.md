# Vibe Coding 协作方式（整合版）

## 一、三方角色

### 1. 用户：产品负责人和最终验收人

- 提出业务目标、真实使用感受和优先级。
- 判断功能是否真正有用、方向是否正确。
- 对业务规则、UI、交互和最终结果进行人工验收。
- 可以推翻当前方案，决定是否进入下一阶段。

用户不需要先给出技术方案，核心问题是：

> 这个东西是不是我真正需要的？

### 2. ChatGPT：需求判断、架构约束和流程控制者

- 先判断问题性质、价值、风险和实现必要性。
- 识别 Bug、Feature、UX 问题、产品逻辑问题、研究问题和个人偏好。
- 主动指出错误前提、过度设计、隐藏风险和范围蔓延。
- 将业务想法整理成明确的规则、边界、POC、Spec 或实现任务。
- 为 Codex 编写精简、可执行的任务提示词。
- 检查 Codex 的实现、测试和报告是否偏离目标。
- **负责正式 Spec Review。** Codex 写完并 Push Spec 后，ChatGPT 直接从 GitHub 读取最新 Spec，检查业务规则、范围、边界、架构一致性、当前实现兼容性和测试要求；只有 Review 通过后 Spec 才冻结。
- 对技术复杂度特别高的 Spec，可以额外让 Codex 做技术可实现性检查，但它只作为补充，不替代 ChatGPT 的 Spec Review。
- 控制 Review、修复、Commit 和 Push 的时机。

### 3. Codex：工程执行者

- 阅读仓库、现有架构、Spec 和相关测试。
- 按任务范围修改代码、文档和测试。
- 运行验证并报告 diff、测试结果和 Git 状态。
- 不擅自重新定义产品、不扩大范围、不顺手重构。
- 原则上不自行 Commit 或 Push，除非任务明确授权。

一句话：

> 用户决定“要什么”，ChatGPT 把它变成不容易做歪的任务，Codex 负责按约束执行。

## 二、总原则

1. **先判断，再实现。** 先确认真正要解决的问题、是否值得做、现有架构是否已经能够解决，以及是否存在更简单的方案。
2. **先找根因。** Bug 先复现、追踪真实调用链，再在共享根因处做最小修复；不要只给单个表象路径打补丁。
3. **保持最小实现。** 复用现有代码和架构，优先标准库、平台能力和已有依赖；不为未来猜测增加抽象、接口、依赖、表、服务或框架。
4. **按业务能力组织 Feature。** 小而完整的能力尽量一次打通 Backend、Frontend、Tests 和必要文档；按风险拆分，不按技术层机械拆分。
5. **真实数据优先。** 未验证的数据、模糊状态和未知值保持 `null`、`Unknown` 或 `PARTIAL`，不制造精确数字、假数据或全 NULL 的假历史记录。
6. **历史事实不覆盖。** 采集异常、下架或数据缺失不应删除、清空或伪造过去有效的 Snapshot、价格、库存、SKU、标题和主图。
7. **状态依赖正面证据。** 解析失败、滑块、空白页、网络失败不能直接推断为下架、离线或库存为零；异常时保留原状态，并区分业务状态与监控状态。
8. **UI 先做最小调整。** 优先调整字号、间距、对齐、Badge、反馈和信息层级，不因单个体验问题重做整页。
9. **所有非平凡修改都要有验证。** 至少保留一个能发现逻辑回归的自动检查，并根据风险补充 targeted tests、full tests、人工验收或 Review。

## 三、标准流程

```text
提出需求或反馈
    ↓
判断价值、问题类型和范围
    ↓
必要时先做 POC 或冻结产品规则
    ↓
编写 Spec
    ↓
Codex 自检并单独 Commit / Push Spec
    ↓
ChatGPT 从 GitHub 读取最新 Spec 并做 Spec Review
    ↓
必要时修订 Spec 并再次 Push
    ↓
Spec 冻结
    ↓
实现与自动测试
    ↓
有对应场景时运行 Playwright 自动 QA
    ↓
按风险分级进行人工验收
    ↓
独立 Code Review
    ↓
修复真实问题并复审
    ↓
Commit / Push
```

### 1. 需求讨论

当用户说“这里不舒服”“为什么这样”“感觉有问题”时，默认先分析，不立即改代码。先判断这是：

- Bug；
- 可用性或视觉问题；
- 产品逻辑问题；
- 研究问题；
- 个人偏好；
- 新需求。

只有用户明确表示“给我提示词”“直接修”“就按这个改”等，才进入实现阶段。低风险、可逆的小歧义可以采用合理假设继续；会显著影响架构、数据、兼容性或用户行为的歧义必须先确认。

### 2. POC

用于验证数据源、网页结构、第三方行为或其他不确定前提。

- 不改正式业务逻辑和数据库状态。
- 只验证可靠信号和边界。
- 保留失败、模糊和 `PARTIAL` 结论。
- 结果写入 `docs/research/`，不自动升级为正式功能。

### 3. Spec

当规则涉及多个状态、页面、数据结构或参与者时，先写正式 Spec。

- Spec 放在 `docs/specs/`。
- **纯 Spec 任务默认允许在自检通过后直接 Commit / Push。** 这样任务完成后，ChatGPT 可以直接从 GitHub 读取最新提交的 Spec，而不依赖用户手动复制全文，再立即进入独立 Spec Review。
- Spec 阶段的 Commit / Push 必须保持聚焦：原则上只提交本轮目标 Spec，以及确有必要且与该 Spec 直接相关的文档；不得顺带提交业务代码、测试、日志或其他无关改动。
- Push 后必须核验远端已包含本轮 Spec（例如确认 `HEAD == origin/main`，或等价地确认目标提交已在远端分支）。
- ChatGPT 在 Spec Review 中检查业务规则、范围、边界、架构一致性、现有实现兼容性和测试要求。Review 未通过时，回到 Spec 窗口做最小修订，再次 Commit / Push 后复审。
- **只有 Spec Review 通过后，Spec 才视为冻结，随后才进入 Implement。**
- 冻结后实现严格按 Spec，不重新设计需求。
- Spec 的局部规则不应反复写入长期架构文档。

### 4. Implement

实现任务必须明确：本轮做什么、不做什么、关键业务规则、测试范围以及是否允许 Commit / Push。

- 先读 Spec、现有实现和测试。
- 只改完成当前目标所必需的文件。
- 不新增未要求的功能、依赖、迁移、抽象或重构。
- 跑 targeted tests，再按风险运行 full tests。
- 已经有 Playwright E2E 覆盖的前端关键路径，按影响范围运行对应自动 QA；不要把已有 Vitest / pytest 逻辑机械重写成 E2E。
- 业务代码实现完成后，通常先不 Commit / Push，等待风险分级人工验收和 Review。

### 5. 自动 QA 与人工验收

自动测试通过不等于完成，但也不要求用户对每个 Feature 重复机械点击全部逻辑。

项目采用三层验证：

```text
Vitest / pytest
→ 逻辑、纯函数、API Contract、业务规则

Playwright E2E
→ 真实浏览器中的关键用户路径：点击、输入、翻页、勾选、筛选等

人工验收
→ 视觉是否舒服、交互是否自然、业务是否真正好用
```

自动 QA 原则：

- E2E 只保护值得长期防回归的关键用户路径，不追求“每条 Spec 验收项对应一条 E2E”。
- 已有 E2E 覆盖的路径，后续 Feature 优先复用或增量补 1～2 个断言/场景，不重复重写整套测试。
- 纯逻辑继续由 Vitest / pytest 保护；真实浏览器行为才交给 Playwright。
- Bug 如果适合自动复现，优先增加最小 Regression Test。
- Frontend E2E 使用受控 Mock 数据时必须与真实 Backend 隔离，不能读取或修改真实工作数据。

人工验收按风险分级：

- **低风险 Feature**：自动测试和相关 Playwright QA 通过后，只做最小体验验收，例如看页面是否正常、操作是否明显别扭。
- **中风险 Feature**：补充关键用户路径人工验收。
- **高风险 Feature**：涉及真实数据写入、永久删除、生命周期、采集、调度、真实外部网站或其他难以安全 Mock 的行为时，保留完整人工 QA。

用户人工验收重点检查：

- 布局、层级和信息密度；
- 时间和状态语义；
- 操作路径、反馈和按钮位置；
- 文案是否易懂；
- 数据是否真的有价值；
- 功能是否值得保留。

人工验收可以推翻原来的实现方向，因此不应为了完成旧清单而自动继续开发。

### 6. Code Review

Review 应独立于实现窗口，分为两个维度：

- **Standards Review**：检查架构、边界、错误处理、重复、性能、数据一致性和测试。
- **Spec Review**：检查实现是否违反冻结的业务规则和范围。

问题按 P0、P1、P2、P3 管理。业务代码进入最终提交前应满足：

```text
P0 = 0
P1 = 0
P2 = 0
```

P3 可以记录为后续优化。Reviewer 只负责发现问题，不直接修改、提交或推送；真实问题回到实现窗口做最小修复，再复审。

Review 默认采用“**一次正式 Review + 一次 Final Gate**”的收敛策略，避免同一 Feature 在多轮 Review 中不断扩大搜索面：

- **实现窗口先自检完整影响面。** 实现完成后，在进入正式 Review 前先按 Spec、架构、测试和高风险状态做一次完整自检，不把明显遗漏留给 Reviewer 逐轮发现。
- **正式 Review 要按根因做全影响面扫描。** Reviewer 发现一个问题后，不只报告当前文件或单一路径，还应检查同一根因是否影响其他入口、状态和调用链。例如并发互斥问题应同时检查 add、single、batch、daily、delete 等相关路径，避免“修一个入口、下一轮再发现另一个入口”。
- **Findings 先按根因聚类，再一次性修完整。** ChatGPT 不机械照单逐条打补丁，而是先合并重复 Finding、判断共同根因和真实影响面，再让实现窗口一次性修复该根因覆盖的全部 P0/P1/P2。
- **Final Gate 以验证关闭为主，不重新无限扩张范围。** 修复后复审重点确认上一轮 P0/P1/P2 已关闭，并检查本轮修复是否引入新的 P0/P1/P2；不重新从零发起无限制的全仓探索，不把纯维护性 P3 在无新证据时升级为阻塞项。
- **正常目标是最多两轮。** 默认目标为 1 次正式 Review + 1 次 Final Gate。只有 Final Gate 发现新的真实 P0/P1，或 P2 属于高风险正确性、数据一致性、安全性、并发或迁移问题时，才继续进入新的修复循环。
- **不为“Review 次数”牺牲正确性。** “最多两轮”是流程收敛目标，不是硬性跳过真实问题的上限；若 Final Gate 发现会影响数据、业务不变量或关键用户路径的真实问题，仍必须修复后再提交。

### 7. Commit / Push

提交前确认：

- Spec、实现、测试和人工验收均完成；
- P0/P1/P2 已清零；
- `git diff --check` 通过；
- migration、测试和必要文档没有遗漏；
- 没有意外的 untracked 文件；
- 使用精确路径 `git add -- <files>`；
- Commit 后 Push，并验证 `HEAD == origin/main` 和工作区状态。

一个完整 Feature 尽量一个聚焦 Commit；Bug、Research、Spec、Feature 和 QA 基础设施等不同性质的工作不要混在同一个 Commit 中。

当一个 Feature 与新的 QA 基础设施同时开发时，优先分别提交。例如“分页 Feature”和“首次引入 Playwright QA”应保持独立 Commit，便于 Review、回滚和后续维护。

**Spec 任务是上述常规提交流程的明确例外：**

- 当本轮任务仅用于新增或修订 Spec 时，默认允许 Codex 在完成自检后直接 Commit / Push，不需要等待人工验收或代码 Review；
- 这样 ChatGPT 可以在 Codex 完成后直接通过 GitHub 读取远端最新 Spec，并立即执行 Spec Review；
- Spec Review 发现问题时，修订仍保持为独立、聚焦的 Spec Commit，并再次 Push 后复审；
- Spec Review 通过后才进入业务代码实现；
- 该例外仅适用于 Spec / 直接相关文档，不自动授权业务代码实现阶段 Commit / Push。

## 四、Codex 窗口和提示词规则

每次生成 Codex 提示词前，ChatGPT 先向用户说明窗口策略：

- **新开 Codex 窗口**：新 Spec、新 Feature、独立 POC、正式 Review 或新的开发阶段。
- **继续当前 Codex 窗口**：同一阶段的小修、人工验收后的调整、Spec 小修或同一 diff 的复审。

**窗口策略属于 ChatGPT 给用户的操作说明，不属于 Codex 任务内容。** 应放在可复制提示词代码块之外，不能写进 Codex 提示词正文，避免 Codex 将“新开窗口 / 继续窗口”误解为需要它执行的任务、环境操作或额外流程。

同时必须说明本轮 Skill 策略。由于不能默认知道仓库中当前有哪些项目级 Skill，**每次编写 Codex 任务提示词前，都应先在当前仓库中检索实际存在的项目级 Skill 及其说明文件，再决定是否使用。**

Skill 判断流程：

1. 先搜索当前仓库中的项目级 Skill 定义、说明文件和相关目录，确认实际存在的 Skill、用途和准确路径；
2. 只基于仓库中实际找到的 Skill 做判断，不凭记忆、名称猜测或过去项目经验假定某个 Skill 存在；
3. 判断当前任务是否能从某个 Skill 中复用有价值的方法、检查清单或执行步骤，而不是要求该 Skill 与当前项目流程 100% 一致；
4. 如果需要，在提示词中同时写明 **Skill 名称 + 仓库内准确相对路径**，并在存在冲突时明确“采用哪些部分 / 不采用哪些部分”；
5. 如果 Skill 中某些步骤与已冻结 Spec、项目架构、协作流程或本轮任务边界冲突，只覆盖冲突部分，不因此自动放弃整个 Skill；
6. 如果没有找到任何对当前任务有实际复用价值的 Skill，则明确写“Skill：不使用”，不要为了使用 Skill 临时扩大任务。

Skill 策略统一写成：

- **Skill：不使用**：已检查当前仓库的项目级 Skill，没有对本轮任务具有明确复用价值且有必要采用的 Skill；直接基于现有仓库、Spec、架构和测试完成。
- **Skill：使用 `<skill-name>`（`<relative/path/to/skill>`）**：仓库中已确认存在该 Skill，且其全部或部分方法对当前任务有明确价值。
- **部分采用 Skill 时必须写清边界**：例如“采用 Spec 整理与遗漏检查方法；不采用 issue tracker 发布步骤，继续使用本项目 `docs/specs/` → Push → ChatGPT Spec Review 流程”。

Skill 使用遵循“最少必要、可选择性复用”原则：

- 每次提示词都必须先搜索仓库中的项目级 Skill，再明确写出“Skill：不使用”或“Skill：使用 `<skill-name>`（`<path>`）”；
- 使用 Skill 时必须给出仓库内准确相对路径，避免 Codex 找不到、误用同名 Skill 或使用错误版本；
- 不得写一个尚未在当前仓库中验证存在的 Skill 名称；
- **Skill 是可复用的方法库，不是必须整套执行的强制工作流。** 可以只采用其中与当前任务匹配的原则、检查方法、步骤或模板；
- 当 Skill 只有部分内容适用时，在提示词中明确列出“采用部分”和“不采用部分”，不要因为某个步骤冲突就把整个 Skill 判定为不可用；
- 反过来也不能以“部分采用”为理由任意忽略 Skill 中与当前任务直接相关的关键约束；被覆盖的部分必须有明确的项目级依据；
- 如果存在多个相关 Skill，只选择完成当前任务真正必要的最小集合；
- 不为了使用 Skill 而使用 Skill；
- 不一次堆叠多个没有明确必要性的 Skill；
- 不因为存在 Skill 就扩大任务范围；
- Skill 不能覆盖当前 Spec、项目架构、本协作方式和本轮任务边界；
- 冲突优先级：**已冻结 Spec / 当前任务明确约束 → 项目架构与协作方式 → Skill 建议**；当前仓库真实实现始终用于校验事实；
- 当任务不需要 Skill 时，明确写“Skill：不使用”。

窗口策略在提示词代码块之外说明；Codex 提示词正文建议直接从 Skill 策略或任务目标开始，例如：

```text
Skill：不使用
```

或：

```text
Skill：使用 `<skill-name>`（`<仓库内相对路径>`）

采用：
- <本轮实际复用的方法 / 步骤>

不采用：
- <与项目既定流程冲突或本轮无关的步骤>

覆盖依据：
- <已冻结 Spec / 项目架构 / 协作方式 / 本轮明确约束>
```

如果需要提醒用户“新开 Codex 窗口”或“继续当前 Codex 窗口”，应在上述可复制代码块之前单独说明，不纳入提示词内容。

例如 `to-spec` 可以采用“把讨论收敛为结构化 Spec、检查遗漏”的方法，但不采用其 issue tracker 发布步骤；Spec 仍保存到本项目 `docs/specs/`，按“Codex Push → ChatGPT GitHub Spec Review → 冻结”执行。

提示词遵循“最小充分信息”：

- 说明本轮目标；
- 说明不做什么；
- 只保留容易做错的关键规则；
- 直接引用已有 Spec，不重复整份 Spec；
- 写明测试和 Git 权限；
- 如果本轮是纯 Spec 任务，Git 权限默认写明：允许在 Spec 自检通过后直接 Commit / Push，但仅限本轮 Spec 和必要的直接相关文档；Push 后验证远端提交成功，以便 ChatGPT 直接从 GitHub 进入 Spec Review；
- 如果本轮是业务代码实现，仍按风险和阶段明确是否允许 Commit / Push，不继承 Spec 阶段的默认授权；
- 尽量使用一个可直接复制的连续代码块。
- 提示词以“完成任务所需的最少信息”为目标，不以篇幅长或约束数量多为目标。
- 能用一句话准确表达的内容，不拆成多句或重复解释；能引用现有 Spec、文档、测试或上一轮 Review finding 的，不在提示词中重新复述全文。
- 在保证任务目标明确、关键约束不丢失、修改范围可控、测试与 Git 权限清楚的前提下，提示词应尽可能简短。
- 只展开 Codex 容易误解、容易做错、本轮新变化或高风险的部分；已冻结且没有变化的规则默认通过引用文档继承。
- 避免为了“显得完整”重复仓库中已经明确的事实、流程、测试清单和禁止事项。

## 五、文档分层

文档是长期项目记忆，不是每次代码修改都要同步的开发日志：

```text
docs/product.md       → 产品长期方向
docs/architecture.md  → 架构原则
docs/data-model.md    → 数据语义
docs/ui-system.md     → UI 规则
docs/coding-rules.md  → 编码约束
docs/specs/           → 某个 Feature 的精确合同
docs/research/        → POC、调研和不确定性验证
```

只有稳定事实或长期规则变化时，才更新核心文档。普通 Feature 的局部规则放入 Spec，POC 放入 Research，普通 Bug 通常只改代码和测试。

## 六、一句话总结

> 用户负责真实使用和产品判断；ChatGPT 负责把问题判断清楚、把规则和流程收敛；Codex 负责严格执行并验证。每次修改都应有明确业务理由，范围尽量小，事实必须可靠。
