# Personal Workbench

## 1. 定位与范围

Personal Workbench 是个人 Windows 本地 Web 工作台；当前稳定业务是 **1688 商品竞争情报**。以我方商品组为中心，保存可靠采集事实、识别客观变化、压缩噪音，帮助运营判断今天先看什么，再进入组内分析和单品证据。

当前职责链：

```text
监控商品 → Snapshot / SKU → ChangeEvent
→ Backend 组级 Attention → Group-first Dashboard
→ Group Detail V1 → Competitor Detail 证据
```

本文件记录当前实现；[Spec 索引](specs/README.md) 说明合同更新关系。[重构计划书](roadmap/competition-intelligence-restructuring-plan.md) 中的未来方案不自动成为现有功能或实现授权。

## 2. 商品身份与管理

- 我方与直接竞品复用 `Competitor`，没有独立 OwnProduct 实体。`ownership` 表示商品身份，`group_id` 表示当前比较组，`group_role` 是兼容组内角色；监控状态和在线状态独立。
- 我方店铺名称配置在系统设置。Backend 仅标准化首尾和连续空白后精确比较真实店铺名，不按标题、关键词、组名或前端缓存识别身份。
- 大屏是唯一“添加监控商品”UI 入口；添加先采集并验证店铺，再原子创建商品、baseline Snapshot/SKU 和成功 CollectionRun。无法确认店铺、重复或校验失败不留下半成品。多链接 UI 逐条提交并保留失败输入，不是新批量添加 API。
- 我方商品与竞品列表分别读取 `ownership=self / competitor`，支持本地搜索、状态/分组筛选和固定每页 10 条分页，选择跨页保留并与筛选结果求交集。
- 我方商品支持单条绑定、更换或解除已有竞品组，目标已有 own 时冲突，不覆盖；批量操作仅停止/恢复监控，永久删除为单条操作。
- 直接竞品支持单条和批量分组、批量停止/恢复、批量永久删除；不允许 self 参与竞品批量分组或批量删除。
- 列表无添加、单条采集或批量采集入口；详情继续承担单品证据与生命周期操作。单商品采集 API 保留，不等于列表仍提供按钮。
- 分组页管理组的创建、重命名、删除与摘要，提供组分析和列表筛选入口；不再人工指定商品身份。删除组解除全部成员关系，保留身份、商品和历史。

## 3. 页面职责与导航

竞品监控导航当前依次为：竞品监控大屏、我方商品、竞品列表、竞品分组、采集任务。首页、自动上架为占位页，系统设置已启用。组分析从大屏或分组进入，不新增独立 Group Detail V2 / 竞争分析导航。

### Group-first Dashboard：今天先看哪些组

- 关注组及三个组级 KPI 来自 `GET /api/dashboard/group-attention`；Backend 完成去噪、等级、原因和稳定排序，Frontend 不再评分。
- 监控商品组数要求当前绑定 self/own 且至少一个直接竞品；关注主列表还要求今日有可纳入 Attention 的直接竞品事件。未绑定、未分组、无变化组不伪装成关注项；无变化组仍可在分组页查看。
- 显示“重点关注 / 建议查看 / 一般变化”、distinct 变化竞品数、最多三条事实原因和检测时间；不显示内部评分，不解释为风险或竞争力。
- 采集异常、采集概览与近 7 天竞品变化趋势沿用 `GET /api/dashboard/today`。独立请求失败局部降级，不能伪装为零变化。
- Header 显示我方店铺、“添加监控商品”和“立即采集”。立即采集覆盖全部 active self + competitor；竞品统计过滤 self，通用采集概览可包含双方。

### Group Detail V1：组内事实与近期动作

- 单一组级读取 API `GET /api/competitor-groups/{id}/detail?days=7|30`，返回 own、直接竞品、比较、今日事件和动作窗口。
- 比较最新有效 Snapshot 的价格区间、MOQ、SKU 数量及完整库存；价格区间重叠不能断言谁更低，任一库存未知不计算总库存。
- 未绑定基准或无可比数据明确显示缺失状态，不制造名次；下架/停止监控仍可追溯最近有效快照，展示采集时间。
- 我方事件与竞品事件分开；今日与 7 / 30 天窗口按 Asia/Shanghai 业务日期、当前组成员关系聚合，不宣称事件发生时已属于该组。
- 当前只有事实差距和事件动作统计，没有公司级排名、同规格 SKU 排名、Own Competitive Position 或经营指标扩展。

### Competitor Detail：单品证据

- 当前概览、最近真实价格变化、商品图库、SKU、最近变化与单商品采集记录；支持停止/恢复、永久删除和单条归组。
- 价格和库存趋势共用 7 / 30 天每日最终成功快照；缺失日期为空点，未知值不变成零。
- 正式首图与图库预览分开，点击缩略图不改写事实。SKU 展示名称解码仅在读取展示层完成，不回写历史。
- 销量仅保留“销量数据待接入”占位，不绘制 POC 数据。

### 采集任务：运行观察与排障

- 当前批量状态来自唯一进程内 BatchRuntime；涵盖手动及自动 Batch，不代表 single / add 的全部活动。Backend 重启后不恢复批次。
- 展示运行、主动休息、风控冷却、人工验证、完成或 idle；明细默认折叠，展开保持 Backend 顺序，不把失败项移到列表前面。
- 历史来自 `GET /api/collection-runs`，是持久化单商品尝试，支持搜索、成功/失败、当前身份筛选及分页；不是持久化批次，也不区分自动/手动来源。
- 不发起、重跑、跳过采集或绕过验证；当前状态与历史请求独立，completed 不由本地 Toast 消失重置为 idle。

## 4. 采集、变化与真实数据边界

正式 Collector 使用 Playwright + 本机 headed Chrome、独立 `.browser-profile`，以 HTML / 内嵌 JSON 解析商品标题、店铺、主图/图库、商品价格区间、SKU 身份/库存/页面展示价格与 Offer 级 MOQ。

自动采集仅在 Backend 运行时检查，启动即检查、之后约每分钟检查；支持关闭、rolling_24h、fixed_daily（电脑本地时区）及 catch_up / skip。成功和失败尝试均计入 due 判断；调度编排复用唯一 Batch Runner，范围是全部 active self + competitor。休眠/关机时不执行，不提供系统唤醒或云端调度。

系统设置保存我方店铺和九项采集配置；Batch 启动时冻结其中五项节奏/风控参数。运行中的 Batch 不因新设置变化。普通单项失败继续后续项；验证走冷却与有限续采，耗尽后需要人工处理。

ChangeEvent V2 正式覆盖商品/SKU 价格、库存方向、SKU 新增/移除/售罄/恢复、MOQ、上下架、标题和主图；旧 `stock_changed` 只兼容读取。首次采集建立 baseline，明确下架不创建空 Snapshot，恢复首轮仅记 product_online 并重建 baseline。异常不清除历史或伪装成下架。

库存下降不等于销量，展示价格不等于最终成交价，检测时间不等于平台变化发生时间。销量研究见 [数据源验证](research/1688-sales-source-validation.md)，仅为研究证据；当前正式模型和 API 没有销量或新经营指标。

## 5. 后续规划与不做范围

Track A：优先在现有事实上定义组内竞争位置、排序与可解释我方定位。Track B：经营指标增量 POC 可并行，只阻塞新指标产品化。具体阶段以重构计划书为准，Group Detail V2、经营观察、企业主体、管理导航融合和市场机会分析尚未实施。

当前不建设 AI 决策、自动改价、自动选品、自动上架业务、多用户、权限、通知、云部署、多平台、代理池或分布式采集。

## 6. 稳定原则与仍需验证

长期保持原始事实可追溯、未知值明确、失败隔离、业务状态与监控状态分离、单一权威读取和最小实现。UI 全局视觉规范见 [ui-system.md](ui-system.md)；系统设置是局部改版试点，其他页面未完成统一换肤。

外部网页结构、登录/验证稳定性、研究接口可访问性和经营字段口径需持续实证；当前代码存在对应功能不代表对未来所有平台行为作稳定性保证。
