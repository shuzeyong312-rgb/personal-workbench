# UI System

## 1. 目标

本文件定义 Personal Workbench 的长期 UI 规则。

它负责约束：

- 全局视觉风格；
- 页面骨架；
- 导航层级；
- 基础组件；
- 状态与语义色；
- 三类 Reference Page 的结构基线。

它不负责逐页业务需求。具体页面展示什么字段、按钮执行什么业务行为，由对应 Feature Spec 定义。

核心原则：

> 新页面应延续现有设计体系，而不是重新设计一套 UI。

---

## 2. 已确认的视觉方向

当前视觉方向已经冻结，不再主动探索新风格。

关键词：

> 浅色高级感 / 蓝紫雾感 / 柔和渐变 / 轻毛玻璃 / 清爽 SaaS / 中等信息密度 / 精致但克制

### 2.1 背景

- 整体为非常浅的冷白、淡蓝、淡紫雾感背景；
- 可以存在柔和的大面积渐变光晕；
- 背景只负责营造空间感，不与正文抢视觉；
- 禁止高饱和大面积渐变、赛博朋克、纯深色大底。

### 2.2 卡片

- 主体内容使用白色或近白色半透明卡片；
- 允许轻毛玻璃质感；
- 使用非常轻的描边、柔和阴影和适度背景模糊；
- 数据密集区域优先可读性，透明度不能过高；
- 统计卡片可加入轻微局部渐变或柔和色彩光晕。

### 2.3 色彩

主色：

- 蓝色 / 电光蓝作为主要操作色和选中态；
- 蓝紫可作为辅助科技感颜色。

辅助语义色：

- 绿色：成功、正常、下降类正向状态；
- 紫色：SKU / 分类类状态；
- 橙色：提醒、价格变化等辅助状态；
- 红色：失败、异常、风险；
- 浅蓝：一般信息、采集中等中性状态。

要求：

- 色彩丰富但克制；
- 不同状态必须同时配合文字或图标，不能只依赖颜色；
- 页面不得自行发明新的主色体系。

### 2.4 字体与数字

- 中文必须清晰易读；
- 页面标题有明显层级；
- 关键数字可以加大加粗；
- 表格正文保持可快速扫描；
- 不使用装饰性字体。

---

## 3. 全局页面骨架

桌面端优先。

所有主要页面保持：

```text
左侧分级导航
+
顶部全局区域 / 面包屑 / PageHeader
+
主内容区
```

主内容区使用统一留白、圆角和卡片间距。

V1 不单独设计完整移动端系统，只保证基础响应式不崩坏。

---

## 4. 左侧导航：Personal Workbench 信息架构

整个产品是“个人工作台”，竞品监控只是其中一个工具模块。

导航基线：

```text
个人工作台

首页

竞品监控
  ├─ 竞品监控大屏
  ├─ 竞品列表
  ├─ 竞品分组
  └─ 采集记录

自动上架
  └─ 后续扩展

系统设置
```

规则：

- 一级导航代表工具 / 系统模块；
- 二级导航代表模块内部页面；
- 当前一级模块展开；
- 当前二级页面明显高亮；
- 二级导航通过缩进、字号、背景和图标层级体现父子关系；
- 不把竞品监控表现成整个产品本身；
- 后续新增工具时继续沿用相同一级模块结构。

左上角品牌区固定表达：

```text
个人工作台
工作提效工具集
```

或语义等价文案。

---

## 5. 顶部区域

统一包含：

- 面包屑；
- 页面标题；
- 一句简短页面说明；
- 右侧主要操作；
- 全局搜索 / 通知 / 用户入口可保留在统一位置。

面包屑用于表达：

```text
个人工作台 / 一级模块 / 当前页面
```

详情页可进一步增加上级页面：

```text
个人工作台 / 竞品监控 / 竞品列表 / 竞品详情
```

不要每页重新设计顶部结构。

---

## 6. 基础组件

V1 优先统一：

- Button
- Input
- SearchInput
- Select
- Card
- StatCard
- Table
- Dialog
- Badge
- Toast
- EmptyState
- PageHeader
- Breadcrumb
- FormField
- LoadingState
- ErrorState
- Pagination
- TrendChart

新页面优先组合现有组件。

不要因为单个页面需求重新创建一套 Button / Card / Table / Badge 风格。

---

## 7. 状态规范

所有数据页面至少考虑：

```text
Loading
Empty
Error
Normal
```

提交操作至少考虑：

```text
Submitting
Success
Failure
```

采集业务至少考虑：

```text
采集成功
采集中
采集失败
未知
```

空状态必须告诉用户下一步可以做什么。

# 8. Reference Page 01：竞品监控大屏

定位：

> 数据总览型页面。

它回答：

> 今天发生了什么？

这是竞品监控模块的总览入口，也是 Dashboard 类页面的视觉基线。

### 8.1 固定结构

```text
PageHeader
↓
核心统计卡片
↓
左：今日发生变化的竞品
右：最近采集状态概览
↓
左：最近变化列表
右：近 7 天变化趋势
↓
快捷入口
```

核心统计卡片当前包含：

- 今日变价商品数；
- 库存变化商品数；
- SKU 变化商品数；
- 异常采集数。

核心模块：

- 今日发生变化的竞品；
- 最近采集状态概览；
- 近 7 天竞品变化趋势；
- 最近变化列表；
- 快捷入口。

### 8.2 Dashboard 规则

- “今日发生变化的竞品”是页面最重要的信息；
- KPI 卡片数量保持克制；
- 图表只展示真正有判断价值的数据；
- 不做传统 BI 大屏；
- 不把装饰性数据放在核心位置；
- 统计卡片可以使用不同轻辅助色增加识别度。

以后其他总览型页面优先参考本页面，而不是重新设计 Dashboard。

---

# 9. Reference Page 02：竞品列表

定位：

> 列表 / 筛选 / 管理型页面。

它回答：

> 我现在监控了哪些商品？

也是未来“采集记录”“自动上架列表”“选品列表”等管理型页面的主要参考。

### 9.1 固定结构

```text
PageHeader + 主要操作
↓
搜索 / 筛选卡片
↓
列表统计信息
↓
主数据表格
↓
Pagination
```

顶部操作：

- 添加竞品；
- 立即采集。

筛选区参考：

- 商品名称 / offerId / 店铺搜索；
- 竞品组；
- 商品状态；
- 是否有变化；
- 采集状态；
- 重置 / 筛选。

表格信息架构参考：

- 商品信息；
- 店铺名称；
- 竞品组；
- 当前价格；
- SKU 数量；
- 最近变化；
- 最近采集时间；
- 商品状态；
- 采集状态；
- 操作。

### 9.2 List 规则

- 搜索和筛选集中在统一卡片中；
- 主操作放 PageHeader 右侧；
- 表格为主体，不使用大量卡片替代表格；
- 商品列可使用缩略图 + 主标题 + 次级描述；
- 状态统一使用 Badge；
- 价格变化可使用数值 + 趋势箭头；
- 操作列保持简洁；
- 次要信息进入详情页；
- 分页固定在列表底部。

以后所有管理型列表优先复用这一结构。

---

# 10. Reference Page 03：竞品详情

定位：

> 详情 / 趋势 / 历史记录型页面。

它回答：

> 这个竞品现在是什么状态，最近发生了什么？

也是未来其他实体详情页的主要参考。

### 10.1 固定结构

```text
PageHeader + 操作
↓
商品概览卡片
↓
趋势卡片组
↓
SKU 信息
+
最近变化记录
+
最近采集记录
```

商品概览区参考：

- 主图；
- 商品标题；
- 店铺；
- 商品链接；
- offerId；
- 所属竞品组；
- 当前价格；
- 商品状态；
- SKU 数量；
- 当前库存；
- 近 30 天销量；
- 最近采集时间；
- 采集状态。

趋势区参考：

- 近 7 天价格趋势；
- 近 7 天销量趋势；
- 近 7 天库存趋势；
- 时间范围允许切换 7 天 / 30 天。

下半区参考：

- SKU 信息表；
- 最近变化记录；
- 最近采集记录。

### 10.2 Detail 规则

- 顶部先回答“它现在是什么状态”；
- 中部回答“它最近怎么变化”；
- 底部回答“具体 SKU 和历史发生了什么”；
- 图表视觉必须与 Dashboard 保持一致；
- 详情页允许信息密度略高，但仍保持清晰分区；
- 不要把所有字段塞进一个巨大表单。

以后实体详情页优先参考本页面。

---

## 11. 三类 Reference Page 的使用规则

开发新页面前先判断页面类型：

```text
总览 / 今日状态 / 核心趋势
→ Dashboard Reference

搜索 / 筛选 / 批量管理
→ List Reference

单个实体 / 趋势 / 历史
→ Detail Reference
```

如果新页面只是已有类型的变体：

> 优先复用结构，不创建第四种页面体系。

只有现有三类页面明显无法承载真实需求时，才新增 Reference Page。

---

## 12. 表格原则

- 列名清晰；
- 行高舒适；
- 信息密度中等；
- 数字对齐统一；
- 商品信息优先采用“缩略图 + 标题 + 次级说明”；
- Badge 统一；
- 操作列简洁；
- 重要变化突出；
- 次要字段不强塞在表格里。

禁止为了展示所有字段造成横向信息过载。

---

## 13. 图表原则

V1 使用简单趋势图。

要求：

- 折线清晰；
- 网格线轻；
- 坐标轴弱化；
- Tooltip 简洁；
- 蓝 / 绿 / 紫 / 橙等色彩语义在同一产品内保持一致；
- 图表卡片与其他卡片使用相同圆角和阴影体系。

不使用复杂 3D 图表或装饰性图形。

---

## 14. 间距与圆角

统一使用 spacing scale：

```text
4 / 8 / 12 / 16 / 24 / 32
```

圆角只保留少量等级：

```text
small
medium
large
```

整体视觉偏柔和、大圆角，但不能过度卡通。

具体 token 在正式前端初始化时集中定义。

---

## 15. 交互原则

- 主要操作明确；
- 危险操作需要确认；
- 加载中禁止重复提交；
- 保存 / 采集后必须有明确反馈；
- 错误说明发生了什么；
- 可恢复错误应给出下一步操作；
- 不为了“高级感”隐藏核心操作。

---

## 16. 动画原则

只使用轻量、有功能价值的动画：

- Dialog；
- Toast；
- Hover / Focus；
- Loading；
- 简单状态切换。

禁止：

- 大量页面转场；
- 弹跳；
- 复杂背景动画；
- 炫技型交互。

---

## 17. AI / Codex 前端开发约束

AI / Codex 开发 UI 时必须：

1. 先读取本文件；
2. 判断当前页面属于哪一种 Reference Page；
3. 优先复用已有布局和基础组件；
4. 保持左侧导航、顶部区域和视觉 token 一致；
5. 不自行引入新的主色、圆角、spacing 或阴影体系；
6. 不因为单页需求重做全局视觉；
7. 不把示例图中的示例数据当成业务规则；
8. 页面业务字段以对应 Feature Spec 为准。

如果现有组件不足：

> 先判断是否属于通用需求，再新增组件。

---

## 18. 与 frontend-design Skill 的关系

frontend-design 负责提高具体实现的视觉质量。

但优先级始终是：

```text
ui-system.md
↓
Reference Page
↓
已有组件
↓
frontend-design
```

frontend-design 不拥有重新定义产品视觉体系的权限。

---

## 19. Reference Page 与 Feature Spec 的边界

`ui-system.md` 定义：

- 页面怎么长；
- 页面怎么排；
- 页面之间如何保持一致；
- 哪种页面参考哪种结构。

Feature Spec 定义：

- 当前页面具体有哪些业务字段；
- 哪些按钮存在；
- 点击后发生什么；
- 权限、验证、异常和业务规则。

例如：

```text
List Reference：
筛选区 → 表格 → 分页

竞品列表 Feature Spec：
具体有哪些筛选项、表格列和业务行为
```

两者不得混淆。

---

## 20. 示例图数据不是产品规则

Reference Page 中出现的：

- 商品名称；
- 商品数量；
- 价格；
- 日期；
- 用户头像；
- 趋势数值；
- 商家名称；
- 示例图片；

全部只是视觉占位数据。

不得直接写死进正式产品逻辑。

---

## 21. V1 暂不建设

暂时不做：

- 完整 Design Token 平台；
- Storybook；
- 深色模式；
- 多品牌主题；
- 动态换肤；
- 完整移动端设计体系；
- 大型组件库；
- 第四套页面视觉体系。

出现真实需求后再增加。

---

## 22. 最终判断标准

一个新页面是否合格，优先检查：

```text
是否明显属于 Personal Workbench
是否能看出与三个 Reference Page 是同一产品
是否清楚
是否好用
是否复用现有组件
是否保持导航与层级一致
是否容易继续维护
```

而不是检查：

```text
是否用了最新 UI 潮流
是否足够炫
是否和已有页面完全不同
```

当前三张 Reference Page 已作为 V1 视觉基线冻结。除非出现明确可用性问题，否则不主动推翻重做。
