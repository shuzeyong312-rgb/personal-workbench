# UI System

## 1. 目标

当前 V1 只需要建立一个稳定、统一、低维护的 UI 基线。

目标不是做完整设计系统，而是避免每个页面都被 AI 重新设计。

原则：

- 清晰优先于炫技；
- 信息密度适中；
- 统一优先于新鲜感；
- 优先复用现有组件；
- 新页面参考已有 Reference Page。

---

## 2. 整体风格

定位：

> 简洁、专业、现代的个人工作台。

视觉方向：

- 浅色界面；
- 大面积中性色背景；
- 白色内容卡片；
- 适度圆角；
- 轻阴影；
- 清晰层级；
- 少量主色用于关键操作和状态。

避免：

- 过度渐变；
- 玻璃拟态；
- 大量霓虹；
- 复杂动画；
- 装饰性 3D；
- 每个模块不同视觉风格。

---

## 3. 页面布局

桌面端优先。

基础结构：

```text
左侧导航
+
顶部页面标题区域
+
主内容区域
```

主内容区域保持统一最大宽度和页面留白。

页面优先采用：

```text
PageHeader
↓
筛选 / 操作区
↓
核心内容
↓
分页 / 辅助信息
```

V1 不专门为移动端重做整套交互，只保证基础响应式不崩坏。

---

## 4. 基础组件

V1 优先统一以下组件：

- Button
- Input
- Select
- Card
- Table
- Dialog
- Badge
- Toast
- EmptyState
- PageHeader
- FormField
- LoadingState
- ErrorState

新页面优先组合这些组件。

不要因为单个页面需求就创建一套新的按钮、卡片或表格样式。

---

## 5. 状态规范

每个数据页面至少考虑：

```text
Loading
Empty
Error
Normal
```

涉及保存操作时，还要考虑：

```text
Submitting
Success
Failure
```

不要只设计“数据正常存在”的状态。

---

## 6. 表格原则

竞品监控 V1 会大量使用表格。

要求：

- 列名清晰；
- 数字右对齐；
- 状态使用 Badge；
- 操作列保持简单；
- 默认不堆砌太多列；
- 重要变化优先展示；
- 次要字段放详情页。

不要为了展示所有数据把首页表格做得过宽。

---

## 7. Dashboard 原则

首页核心任务：

> 让我快速看到今天哪些竞品发生了变化。

首页优先展示：

- 今日发生变化的竞品；
- 变化类型；
- 旧值 / 新值；
- 发生时间；
- 进入详情页的入口。

V1 不堆大量装饰性 KPI 卡片。

只有真正有决策价值的数据才放首页。

---

## 8. Reference Pages

V1 先认真做好少量 Reference Page：

1. Dashboard
2. Competitor List
3. Competitor Detail
4. Competitor Group
5. Settings / System Status（如后续需要）

其中：

- Competitor List 作为列表页参考；
- Competitor Detail 作为详情页参考；
- Dashboard 作为首页信息层级参考。

新页面开发时优先参考已有页面，不重新定义视觉体系。

---

## 9. 颜色原则

不要在每个页面定义自有颜色。

只保留：

- 背景色；
- 卡片色；
- 主文字；
- 次级文字；
- 边框；
- 主色；
- 成功；
- 警告；
- 错误；
- 信息。

具体色值在前端初始化时统一确定并集中管理。

变化状态建议保持语义一致：

- 涨价 / 风险：错误或警告语义；
- 降价 / 正向变化：成功语义；
- 普通信息：信息语义。

不要仅依赖颜色表达状态，必须同时有文字或图标。

---

## 10. 间距与圆角

统一使用固定 spacing scale，不允许页面里大量随意写间距。

例如：

```text
4 / 8 / 12 / 16 / 24 / 32
```

圆角只保留少量等级。

例如：

```text
small
medium
large
```

具体 token 在前端初始化时统一定义。

---

## 11. 字体原则

V1 不引入复杂字体体系。

要求：

- 中文清晰；
- 数字易读；
- 标题层级明确；
- 正文不过小；
- 表格数据保持可扫读。

不要用过多字体、字重和字号。

---

## 12. 交互原则

操作必须可预测。

要求：

- 主要操作明确；
- 危险操作需要确认；
- 保存后有反馈；
- 加载中禁止重复提交；
- 错误信息说明发生了什么；
- 空状态告诉用户下一步可以做什么。

不要为了“高级感”隐藏必要操作。

---

## 13. 动画原则

只使用有功能价值的轻量动画，例如：

- Dialog 出现；
- Toast；
- 简单状态切换；
- Loading。

不要添加：

- 大量页面转场；
- 炫技 Hover；
- 无意义弹跳；
- 复杂背景动画。

---

## 14. 前端开发约束

AI / Codex 开发 UI 时必须：

1. 先读本文件；
2. 先找现有 Reference Page；
3. 先复用已有组件；
4. 不引入新的视觉体系；
5. 不随意新增颜色、圆角、spacing；
6. 不因为单页需求重做全局样式。

如果现有组件不足：

> 先确认是否属于通用需求，再决定是否新增组件。

---

## 15. 与 frontend-design Skill 的关系

frontend-design 用于帮助确定具体页面的视觉实现质量。

但它必须服从：

```text
ui-system.md
+
已有 Reference Page
+
已有组件
```

Skill 不拥有重新定义整个项目视觉体系的权限。

---

## 16. V1 不做

暂时不做：

- 完整 Design Token 平台；
- Storybook；
- 复杂主题系统；
- 深色模式；
- 多品牌主题；
- 完整移动端设计体系；
- 动态换肤；
- 大型组件库封装。

只有出现真实需求后再增加。

---

## 17. 判断标准

一个新页面是否合格，优先看：

```text
是否清楚
是否统一
是否好用
是否复用了现有组件
是否容易继续维护
```

而不是看：

```text
是否足够炫
是否用了最新设计趋势
是否和上一个页面完全不同
```
