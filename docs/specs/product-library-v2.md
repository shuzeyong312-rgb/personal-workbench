## 1. 字段、来源和模板

模板下载入口提供一个 `.xlsx`，仅“产品清单”一个工作表，表头严格按以下顺序；一行一款，不设临时 ID、图片列或说明工作表。上传时填写并确认一次供应商名称，不按文件名猜测。文件名、上传时间、行号由系统记录，仅原文明确时记录原件页码；不保存文件本体或图片，预览须提示用户自行保留原件。

| 列 | 归属及含义 |
|---|---|
| 分类 | 产品主资料，普通文本，可空 |
| 产品型号 | 产品主资料，文本，可空，保留前导零 |
| 产品名称 | 产品主资料，文本，必填 |
| 产品参数 | 产品主资料，普通文本，可空，保留换行与原文 |
| 批发价 | 供应商来源的出厂批发价原文，可空；多规格在同一单元格分行或用分号分隔 |
| 控价 | 产品主资料，独立普通文本，可空；绝不参与采购成本或客户报价计算 |
| 卖点 | 产品主资料，普通文本，可空 |
| 备注 | 供应商来源普通文本，可空；MOQ、运费、税费、包装、售后、质保、定制等条件按原文保留 |

每条来源按实际模板版本保留原始列原文及独立备注；旧六列来源不得伪造八列原文。同产品不同供应商的备注不覆盖、不合并；同供应商不同文件的条件有差异也各自保留，详情将条件与来源一起展示，报价选择时可查看来源条件，不自动按结构化条件计算或推测。主资料的分类、参数、控价、卖点有差异时逐字段对比；保留现值为默认，明确选择才更新，空输入不清空。来源文本保留，即使主资料不更新；跳过整行不写该行。

新版文件按严格八列表头、顺序及单工作表识别；缺列、额外列/工作表、损坏或文件超限拒绝整个文件；公式和字段超限定位为行错误，不能提交该行。空值是未知，不是 0；文本统一换行符、去首尾空白，不截断。混合供应商且不能可靠判断归属时停止受影响行，提示先拆分文件，不猜测。遵循现有上传大小和安全校验；明确 Excel 附件不保存并要求用户确认。

### 旧 V1 六列兼容与型号单元格

旧 `.xlsx` 保留 `产品数据` 工作表第 1 行的严格六列表头：`产品型号、产品名称、产品参数、产品卖点、批发价、价格备注`。兼容原模板的 `产品数据` + `填写说明` 两表结构；说明表可缺省，其他非业务工作表沿用旧规则忽略，不读取其业务数据；仅当存在四张 V2 专属工作表 `参数明细`、`规格款式`、`价格明细`、`资料索引` 中任一张时按旧混合版本检查拒绝；`产品数据` 和 `填写说明` 均不是拒绝条件。`产品数据` 的隐藏表/行/列、合并单元格、额外非空列、行数、公式与错误单元格继续沿用 V1 安全和行级错误规则，不能把旧说明表当成新模板的额外业务表拒绝。

解析后统一映射到八列：分类和控价为空，型号、名称、参数同名映射，产品卖点 → 卖点，价格备注 → 供应商来源备注，旧批发价 → 批发价原文和旧数值事实；上传供应商只填一次。预览仍按新身份、来源、冲突和事务规则处理；旧数字价标记“待确认出厂语义”，不可因导入或用户普通确认导入自动成为合格报价。来源证据与回执保留实际模板版本（V1 六列或新八列）、原工作表名、原 Excel 行号及原始六列值；仅供计算与预览的统一八字段映射中分类和控价为缺失，不能伪称原件存在这两列。保留原始字段值而非声称原始文件二进制已保存，新文件只推荐八列。

新版下载模板将型号整列的数据填写区域预设 Excel 文本格式 `@`，并提示输入前导零型号为文本。两种模板对型号的非空数字、日期、布尔及公式单元格一律按行报错、不得自动转字符串、根据显示格式补零或推测原文；用户须在 Excel 中将单元格先设为文本并重新输入原始型号，再重新上传。仅修改格式不能恢复 Excel 已丢失的前导零，原始型号不确定时须核对原件；不能静默生成错误身份。空型号仍允许。

### 长度及行数边界

新八列及手动编辑统一限制：分类、型号、名称最多 200 字符；名称必填；产品参数、卖点各最多 10000 字符；控价 `control_price` 最多 2000 字符；批发价原文和来源备注各最多 10000 字符；上传供应商名称最多 200 字符，来源文件名/原件页码各最多 500 字符。长度以统一换行及去首尾空白后的 Unicode 字符数计，不按字节；单元格或字段超限时指出行号、列名和上限，标记该行不可提交，允许跳过或修正后重新预览，禁止截断或部分保存该行。源原文与统一映射均须完整保存，超限不能以截断证据来绕过校验。旧六列沿用其既有长度上限（参数/卖点 10000、价格备注 2000、型号/名称 200），金额按旧数值规则校验。

新八列最多 1000 个物理数据行（Excel 第 2–1001 行，中间空行占位置）；任意非空单元格超出第 1001 行拒绝整个文件，样式空尾行不计。沿用 5 MiB 文件上限及现有 ZIP/文件安全限制。预览行级校验失败的行不可提交，合法行可明确处理；结构错误或超文件/行数上限拒绝整个文件，确认写入仍全事务。

### 控价映射

在产品主表新增独立可空文本字段 `control_price`（最多 2000 字符）；迁移旧产品初始化为 NULL，不从 `price_note`、历史零售价或旧价格推断。产品 API 创建/更新/详情读写独立 `control_price`，手动编辑可明确保存文本或 NULL 清空；八列导入“控价”映射到该字段，预览逐字段比较，导入空值保留旧值。详情标注控价并保留换行；旧六列无该字段，映射为空且不覆盖既有控价。`price_note` 原样只归历史供应商来源备注，不是控价。控价不能参与采购成本、报价资格、报价公式、人工报价核验或客户文件导出；直接调用 API 也必须遵守同一隔离。

## 2. 身份与冲突

产品身份为规范化的 `(型号, 名称)` 精确匹配，供应商不参与。型号/名称仅将 CRLF、CR 统一为 LF 并去首尾空白；空型号统一为 NULL，名称不可空。内部空格、大小写、全半角、标点、Unicode 字符不改写，按 BINARY 精确比较；不将数字型号当文本自动补零或猜测。上传需保留型号为文本。空型号同名仅匹配空型号，不与有型号自动归并；同型号不同名称及同名不同型号保持独立。

为空型号产品补充型号时，先精确检查目标身份：未占用则经用户确认后更新原产品并保留 ID、来源及历史；已占用则拒绝更新，展示两个产品及差异，人工处理，不自动合并。导入有型号的同名新行遇到已有空型号同名产品时，作为潜在重复提示，用户可明确选择保留为新产品或取消并先在详情修正原产品；不能自动追加到空型号产品。反向（导入空型号而已有同名有型号）同样提示，明确选择新建或取消。数据库在写锁内重验身份及候选版本；文件内同一身份重复行阻止该身份组并标行号，不静默合并。

## 3. 供应商、报价和来源证据

最小逻辑关系：一个产品有多个供应商来源；一个 `(产品, 供应商, 规格标签)` 有至多一条当前有效报价及零到多条历史报价版本；一个报价版本可关联多个来源证据，一个来源可支持该行多个规格报价。持久化至少包含：报价键（产品、规范化供应商、规格标签，唯一键）、追加式报价版本（报价键外键、版本序号、金额、币种、单位、资格状态及确认信息、创建时间），以及报价版本与来源证据关联表（版本 ID、来源 ID 联合唯一及外键）；报价键指向至多一个当前版本，历史版本持久保留。当前指针须通过约束/事务验证只指向本键版本。证据关联的多对多关系不能以单一 `source_id` 覆盖前一证据；不得通过覆盖一行及递增并发 version 冒充历史。规格仅为普通文本标签，不建立规格管理实体。供应商名称按现有规则统一换行、去首尾并折叠连续空白后精确匹配；不做别名或模糊匹配，名称不同视作不同供应商。规格统一换行、去首尾空白后精确 BINARY 比较，空规格为独立键；内部字符、大小写、全半角不折叠。

来源证据以实际上传的完整文件字节 SHA-256 内容指纹、供应商规范化值和工作表行号组成幂等键；文件名为展示元数据，不参与唯一判断。相同字节改名重传同供应商同一行复用证据；相同文件名但内容不同须分别保存；同字节用于不同供应商不得互相吞掉。指纹只证明上传文件字节相同，不证明内容语义等同；历史未保存原文件的来源指纹标记未知，不伪造或按文件名去重。改动文件但该行相同可保留新证据。文件、行及其报价证据关联在事务内去重。

同价不等于相同交易条件：每条来源独立保留 MOQ、税费、运费、包装、售后、质保等条件原文及来源版本；不得将条件合并成报价版本的共同事实或覆盖其他来源。客户报价前展示同价关联来源的条件差异，由用户明确选择一个支持该价格的来源，或在核对相关来源后明确填写并确认最终采用条件；即使来源只有一条，也须确认其条件；条件未知时显示未知，单纯确认“未知”不算解决，须由用户明确填写可采用的最终条件并确认。冲突未裁决、最终条件仍未知或未确认时不计算自动报价、不接受作为可导出的行，也不能静默套用全局税运费规则。选来源不等于自动确认条件。

相同产品、供应商、规格、明确金额/币种/单位相同：复用当前报价并追加新来源证据；完全相同证据重放不新增。价格不同：预览对比并要求明确“更新”或“保留”；更新时旧版本连同其证据保留为历史，新版本成为唯一当前值且关联新证据；保留时当前值不变，新来源原文仍可查，但不能错误地作为旧报价的佐证。不同供应商独立。数据库约束和写锁重验唯一当前键，避免并发产生两条；来源备注变化不静默覆盖其他来源。

## 4. 批发价文本和报价资格

标准八列的“批发价”是用户填写/确认的**出厂批发价**，不是由原始文件自动识别；模板提示数字默认人民币元/件。单个纯数字（例如 `26`）代表无规格、CNY 元/件；分行规格采用 `规格：金额`，例如 `5000mAh：26`、`10000mAh：32`，均按模板约定为 CNY 元/件。也接受明确写为 `5000mAh：26元/个` 或 `26元/件`；“个”按模板的每件计价。金额非负、最多两位小数、不超过 999999999.99；0 是明确数值，不等于空。原文始终保留。全角或半角冒号分隔规格和价格；多规格可用换行、中文分号 `；` 或英文分号 `;` 分隔，也可混用，先统一换行再按这些分隔符切分并去片段首尾空白，空片段忽略。除单个无规格金额外，每个非空片段必须恰好有一个冒号、非空规格标签和一个可确定金额；同格重复规范化规格、孤立无标签金额、标签本身含分隔符或冒号均视为歧义，整格待核对，不部分生成报价；不得靠顺序猜规格。同格同规格多价、区间、面议、公式、附带条件、币种/单位不明或非 CNY/件、解析失败时保留整格原文并标待核对，不创建可计算报价；用户修正模板后重新上传。其他明确单位或币种不换算。不能从备注提取金额。

若单元格注明一件代发、零售、控价、建议零售价等非出厂批发语义，或其类型有疑义，即便含数字也只保留原文并标待核对，不因列名自动授予资格。出货价等语义未经确认也不推定为出厂批发。采购报价仅允许选择已确认语义、金额、规格及 CNY/件均明确的当前报价；无报价显示“无报价”，不自动选最低价或唯一项，须明确选择供应商及规格。控价、历史不合格价格、备注和来源不作采购成本。

### 资格状态与状态转换

资格属于每个持久化报价版本，和“当前/历史”是两个独立维度：`pending`（待核对）、`eligible`（已确认合格出厂批发价）、`ineligible`（已确认非出厂批发价）。只有**当前**且 `eligible`、金额/币种/每件单位及产品/供应商/规格绑定有效的版本可参与计算；历史版本即使曾合格也不可用于新报价。

- 标准八列中无非出厂语义冲突、可解析的价格，在预览明确告知列语义并由用户确认导入后生成 `eligible` 当前版本；不明确的原文为 `pending`，不生成可计算金额。旧 V1 数字价（含旧文件及旧库）初始为 `pending`，普通导入确认不构成出厂语义确认。PR #7 `is_default_wholesale` 只作为历史事实保留，不能直接赋予 `eligible` 或自动选价。
- 对 `pending`，用户核对来源后显式确认出厂语义且金额、币种、单位、规格均明确，才能转 `eligible`；确认是一件代发、零售、控价等非出厂价则转 `ineligible`。不可把未知值、非采购类型或不同币种/单位强行确认成合格。
- 已合格报价被证实类型错误时，显式复核可转 `ineligible`；撤销确认或发现证据不足转 `pending`。资格变更须事务内持久化不可覆盖的审核记录（版本 ID、前后状态、确认依据及时间），并令报价快照失效；保留原文；变价创建新版本并重新判断资格，不继承旧版本确认。若不可拆分的原文没有确定规格/金额，仅保存待核对来源，不创建虚构报价键；完成核对后再创建待确认报价。
- 客户报价入口和服务端均要求用户显式选定具体供应商及规格（无规格需显式选“无规格”）和该版本；禁止沿用旧默认价/唯一价自动选择，忽略 `is_default_wholesale` 及主表默认价作为选价信号。选择失效、资格变化或版本变化则拒绝并重新预览。

旧 V1 `wholesale_price_cents` 只证明旧系统的“批发价”数值及旧 CNY/件约定，不证明厂家原始价格类型：精确保留分值、旧来源和历史语义，标“历史批发价，待确认出厂语义”，默认不可作为新客户报价基准；用户核对后明确确认才能作为合格当前报价，不能静默转换。旧客户报价若依赖该价须提示选择/确认，不承诺无交互延续。为避免双重事实，不能把 PR #7 `legacy_backfill` 和旧主表同一数值回填成两条报价。

### 手动来源与报价

手动新增报价时必须明确产品、供应商名称、规格（可明确选“无规格”）、价格原文及来源条件；创建 `manual` 来源记录，保存用户输入、创建时间及条件，文件指纹、文件名、工作表和行号均为 NULL，不伪造文件。以手动创建请求的幂等键防止重试重复，不能用空文件指纹合并不同手动来源。新手动报价初始为 `pending`，用户另行显式核对出厂批发价语义、金额、CNY/件及条件后方可转 `eligible`；不因保存或导入确认自动升级。变价走新版本及同键并发规则。停止 PR #7 的 `is_default_wholesale` 自动选价和 `wholesale_price_cents` 投影/双向镜像；旧字段仅保存历史原值，不作为新业务价格权威，不用于筛选、排序、报价计算或自动回写。

### 详情与客户报价

产品详情以主资料和供应商报价为主，备注随来源展示；来源与历史次级展开，不出现参数明细或多价型管理。手动 CRUD 和搜索须遵守本合同，旧编辑入口不得绕过报价资格或误覆盖来源。客户报价快照绑定所选产品、当前报价版本、实际采用的来源 ID/版本或明确确认的最终条件及其依据来源、原文条件、用户确认、规则、最终覆盖值；任一来源、条件、资格、产品或版本变化均失效并重新预览。仅在条件明确确认后，用户可明确应用全局报价规则；规则与来源条件不一致时须在最终条件中明确确认，不可自动当成来源事实。服务端预览和导出再次校验归属、当前状态、确认和快照摘要；拒绝跨产品、失效或无资格价格。沿用客户文件白名单和敏感词复核；成本、控价、供应商、来源、内部 ID、备注不得泄漏到客户文件。

人工最终报价仅覆盖本次客户售价，不改变供应商报价、资格、来源条件或成本。必须先选择并核验当前合格采购报价、来源及条件；无合格成本或条件未确认时，不得以人工售价绕过门禁而计算/导出。保留原采购成本用于比较，低于成本标风险并要求显式确认；人工售价、核验结论及条件与快照一起绑定，变化须重算重确认。旧版允许无成本人工报价的行为在本目标合同中被覆盖。

### 删除、归档与身份占用

产品普通删除改为软删除（归档），记录删除时间并提升并发版本；普通列表、搜索、客户报价排除归档产品，历史来源、报价版本、证据关联与历史回执不可级联删除，旧 `ON DELETE CASCADE` 路径不能用于普通删除。归档产品仍占用规范化型号+名称唯一身份，导入同身份时显示已归档及来源，默认不写入，用户明确选择恢复原产品（复用 ID，重验版本及身份，重新预览）或跳过；不能自动新建、自动恢复或合并。手动新增同身份同样提示恢复或取消，数据库唯一性含归档行。恢复后价格仍须重新选择并完成资格和条件确认，已归档期间的旧报价快照失效。普通来源/报价删除只能停用或归档并保留完整历史、证据及回执，禁止物理删除；归档报价不可用于新的计算。归档/恢复/停用同事务记录与并发校验，历史回执不因状态变化失效。物理清除不在本期范围。

## 5. 预览、提交和重放

逐行显示八列、异常、主资料差异、每个规格报价的当前/新值和各自决策。需要核对的原文不作为可计算报价；可跳过该行或保留为待核对来源。未处理冲突阻止确认；每行跳过只作用该行，重新预览清空旧决策。确认在写锁内重验产品、身份候选、当前报价及来源快照/预览版本；任何变化或预览过期要求重新预览。产品、来源、报价版本、证据关联和回执在同一事务提交或全部回滚。重复确认相同请求重放 committed 回执；旧 ready 预览失效，历史 committed 回执保持原决策摘要查询和幂等重放。

## 6. 历史迁移及未发布 PR #7 收敛

源码事实：`20261029_20` 预检旧身份冲突并建立型号+名称索引；`21` 增加主表分类/`structured_attributes`、规格/来源/价格表，为每个旧产品建立 `legacy_backfill` 来源，以原 `manufacturer_name` 填 `source_company`，并把非空 `wholesale_price_cents` 回填为 `批发价`、CNY/件、默认价。`LibraryProductPrice.version` 是并发版本，现有代码没有可假定完整的价格历史表；不得虚构以前被覆盖的版本。生产库是否已迁移和各隔离库实际状态本轮未检查。

| 旧数据 | 收敛规则 |
|---|---|
| `manufacturer_name` | 对已有行保留原值、主产品 ID 和首录公司语义，并映射为历史来源的供应商标签，不声称是真实生产厂家；与已有 legacy 来源核对去重。迁移将旧主表该列改为可 NULL（SQLite 表重建需保留行、索引、外键并原子验证），历史值不改；新产品写 NULL，不接受空字符串、虚构厂家或首个供应商填充。新 API 不要求也不以它维护供应商，供应商只写来源。旧字段只读历史兼容，不影响身份。 |
| `wholesale_price_cents` | 按分精确保存历史批发价与旧 CNY/件合同，关联上述来源；未知出厂语义、默认不可用于新客户报价，待人工确认；零值保留。与已回填记录按明确 legacy 关联核对，冲突则停止迁移，不猜取权威值。 |
| `price_note` | 原文逐字保留并关联该历史供应商来源备注；无价格也保留。不得从中提取或猜测价格/控价。旧主字段作为兼容存档保留至验证完成。 |
| 产品和规格 `structured_attributes` | 完整 JSON 原样保存在可追溯历史存档，包含来源引用、条件和冲突；产品原有 `parameters` 原文不覆盖。不得仅拼接文本后删除唯一副本；新导入不再生成结构化参数。 |
| PR #7 规格、来源、价格 | 保留 ID 映射、原始全部字段、时间、版本、来源及关系在只读历史存档；能明确确定产品、供应商、规格、出厂语义及 CNY/件的记录可作为候选，仍须解决同键多条当前报价；非批发、控价、零售、歧义或不合格价格仅历史可查，不参与计算。冲突列出原 ID/差异并阻止自动选择；保留备注、税运费/MOQ 等原文/原字段，不丢事实。来源缺失或规格无法无损表达时保留存档并人工核对。 |
| 现有历史版本与回执 | 若某环境另有历史或备份，盘点并原样保留及映射；没有历史的版本不能补造。保留所有 committed 回执原 payload、决策摘要及查询/重放语义，旧 ready 失效。不要把隔离环境视为可清空。 |

### 五业务工作表的只读归档及物理落点

PR #7 的五项是 Excel **工作表**“产品数据、参数明细、规格款式、价格明细、资料索引”，不是五张同名数据库表。已应用 PR #7 的环境在切换前构建完整、不可变、只读的历史快照：保留原产品数据及 ID、原主表和规格 `structured_attributes` 的完整 JSON（包括数组顺序及引用）、`library_product_variants`、`library_product_prices`、`library_product_sources` 所有行的原 ID、所有字段、时间、并发版本和关联关系；保留旧 `library_imports` 原预览/回执及其状态、摘要和原 ID。五项工作表对应的数据及能恢复其关系的快照一起归档，不依赖原 Excel 曾被保存。不存在原始字段/行的环境标缺失，不凭模板重建或虚构。

旧主产品表仍可作为新主资料的物理基础，故不能把整张在用 `library_products` 简单设为只读：先在同一一致性事务复制其旧行与结构化 JSON 到独立历史快照，再允许新业务维护主资料；旧规格、价格、来源表或其无损独立副本必须只读保留，并保留可解析到快照产品的旧外键/映射。新业务读写只使用新主资料、来源、报价版本及证据关联，不直接读写旧五项数据参与身份匹配、选价或计算。历史查询/审计和迁移核验可只读访问归档；旧 committed 回执仍按原合同重放。归档访问不能触发新业务写入或作为自动资格证据；实施中在权限/接口和数据库层设置写入阻断并测试。不得在迁移、清理或部署时提前删除这些旧数据，删除政策不在本轮授权。

实现时先盘点每个目标环境实际 revision、记录、外键、回执和备份。对未应用 20/21 的旧库，以实际已发布 head 为父版本形成简化迁移；未发布 PR 的五表代码与迁移链收敛，不修改已发布历史 revision。已应用 20/21 的环境必须采用可验证的前向转换路径，保留原始记录及映射，不通过删库/重建或降级假设数据可丢弃；若无法无损映射或识别冲突，停止该环境迁移并输出报告。旧五表模板提示废弃，不再导入。

迁移仅先在隔离副本演练：停写，取得并验证一致性备份；在 SQLite 写锁/事务中做完整性、身份与报价冲突预检、建结构、回填、索引和 revision stamp，任一步失败全部回滚，保持原库与版本不变并可重试。逐项核对数量、ID 映射、金额、完整原文、引用、回执、外键及资格。已成功迁移且产生新写入后禁止 drop 表降级：停写，导出备份后的产品、来源、报价、历史和回执增量，恢复验证过的备份，再人工协调增量；不声称自动无损降级。正式操作需另行授权。

## 7. 验收及门禁

1. 模板下载为单表八列；字段/行数边界、超限不截断、原六列证据与八列映射、四张专属表拒绝分别验证；标准八列及旧六列（含说明表有/无）导入、数值型号拒绝并提示重新输入、百行、空值/前导零、公式/错列/异常文件、混合供应商及无图片均验证；不支持原始 PDF/厂家表自动解析。
2. 数字、换行和中英文分号混合规格、歧义分隔、明确单位、重复规格、含糊价、代发/零售/控价、超范围和空值逐项验证；任何非合格价格不得参与客户报价，旧 V1 明确确认前不可用；覆盖各状态转换、取消确认、旧默认标记伪造及单条报价不自动选择。
3. 同价来源条件冲突/未知、选择来源或最终条件确认、人工售价绕过门禁、条件快照失效均验证；跨供应商备注独立；同价多来源、文件改名与同名不同内容、同源重放、变价新版本、保留旧值、并发和单当前报价约束覆盖；逐行决策、跳过后重新预览、失败回滚及回执重放验证。
4. 历史厂家值与新产品 NULL、控价 API/导入/编辑及成本隔离、软删除/恢复和归档身份占用均验证；空型号补全冲突和潜在重复、身份精确匹配、旧库与已写入 20/21 的隔离副本、所有字段/来源/结构化参数/回执保留、归档只读且不参与新业务、注入失败恢复均验证。历史版本不得凭并发 version 推造。
5. 后续实现运行相关后端 pytest、前端 Vitest/typecheck/build 和桌面/窄屏人工验收；客户文件全内容检查成本、控价、来源和备注不泄漏。本轮不连接或迁移正式库。
6. 实施完成后对固定代码提交进行独立 Code Review；不合并 PR #7、不部署。
