# 竞品组中心化 / Group Intelligence V1

状态：正式产品方向 Spec。基础事实层、ChangeEvent V2、我方角色绑定已实现；Group Detail / 组级读取 contract 尚待实现。

## Problem Statement

当前项目已经完成“竞品分组管理 V1”：用户可以创建、重命名、删除竞品组，将竞品归组或移出分组，查看分组 Summary，并进入按组筛选的竞品列表。

上一阶段的 `competitor-groups.md` 明确限制了范围：竞品组只维护我方商品型号，不维护我方商品链接、价格、SKU，也不提供 Group Detail Page。这是当时正确的分组管理边界，不是实现错误。本 Spec 定义的是其后的产品阶段，不删除、不改写上一阶段的历史语义。

现在的核心问题是：系统知道“A19 组里有哪些竞品”，但仍不知道“哪一个是我自己的 A19”，因此用户仍需逐个打开竞品详情，手工拼出我方商品面对的价格、起批量、SKU、库存和近期动作。

产品需要从“所有竞品今天发生了什么”逐步转向“每一个我方商品当前面对什么竞争环境”。竞品组应从分类文件夹升级为围绕一个真实我方 1688 商品建立的竞争分析单元。

## Solution

Group Intelligence V1 将一个竞品组正式定义为：

> 一个我方真实 1688 商品，以及围绕该商品手动维护的直接竞品集合。

一个组必须能够回答以下问题：

1. 我方商品当前处于什么事实位置：价格、起批量、SKU 数量、完整库存，以及与竞品的可比较位置。
2. 今天这个组发生了什么：哪些竞品降价、涨价、库存变化、SKU 变化、上下架或修改商品内容。
3. 最近谁动作最多：近 7 天 / 30 天各竞品发生了多少客观事件，以及事件按领域如何分布。
4. 我方有哪些可验证的事实差距：有多少竞品价格明确低于我方、起批量低于我方、SKU 更多或完整库存处于不同位置。

V1 只输出事实、对比和事件聚合，不输出竞争力评分、风险判断或运营建议。

### 与上一阶段的边界

- `competitor-groups.md` 继续代表已经完成的“竞品分组管理 V1”。
- 该文档中的“V1 不维护我方商品链接、价格、SKU”和“不做 Group Detail Page”，只约束上一阶段。
- 本 Spec 新增“我方基准商品”概念和 Group Detail，不表示上一阶段设计错误，也不修改旧 Spec。
- `docs/product.md` 等长期文档本轮不修改；待本阶段实现、测试和真实运行完成后再统一同步“当前已实现”内容。

## User Stories

1. 作为个人工作台用户，我希望一个竞品组明确绑定一个我方 1688 商品，以便知道所有对比的基准。
2. 作为用户，我希望一个组最多只有一个我方基准商品，以便页面不会出现多个“我方价格”。
3. 作为用户，我希望可以使用现有的商品链接添加流程登记我方 1688 商品，以便不引入第二套商品采集流程。
4. 作为用户，我希望我方商品与竞品使用同一套采集和历史快照，以便比较结果可追溯且口径一致。
5. 作为用户，我希望旧的未绑定竞品组仍然可以正常查看和管理，以便升级不会破坏已有分组。
6. 作为用户，我希望未绑定组明确显示“尚未绑定我方商品”，而不是把组名或某个竞品猜成我方商品。
7. 作为用户，我希望在组详情看到我方商品当前价格、起批量、SKU 数量和完整库存，以便先了解自己的事实位置。
8. 作为用户，我希望看到我方与每个竞品的价格、起批量、SKU、库存和最近变化，以便一次完成横向比较。
9. 作为用户，我希望缺失价格、SKU 数量或最近变化时看到未采集状态，而不是看到推测的 0 或默认值。
10. 作为用户，我希望库存不完整时看到未知，而不是把未知库存当作 0。
11. 作为用户，我希望看到今天该组的变化事件，并按竞品聚合，避免逐个打开详情页。
12. 作为用户，我希望同一竞品当天发生多个事件时仍能看到事件总数和各事件类型，而不是被合并成无法追溯的一条摘要。
13. 作为用户，我希望区分我方商品发生的变化和直接竞品发生的变化，以便“竞品变化数”不会把我方自身变化算进去。
14. 作为用户，我希望看到近 7 天和近 30 天谁动作最多，并看到价格、库存、SKU、起批量、上下架、标题和主图等客观事件的数量。
15. 作为用户，我希望动作次数来自真实 ChangeEvent，而不是来自评分、风险模型或库存下降的销量推断。
16. 作为用户，我希望看到明确低于我方价格、低于我方起批量或 SKU 多于我方的竞品数量，以便识别事实差距。
17. 作为用户，我希望价格区间重叠或任一侧缺失时不被错误归类为更低或更高。
18. 作为用户，我希望从组详情进入单个竞品详情，查看原始快照、SKU、趋势、变化和采集记录作为证据。
19. 作为用户，我希望从组详情进入现有竞品列表继续管理监控对象，而不是在 Group Detail 中重复实现完整管理功能。
20. 作为用户，我希望停止监控某个商品不会删除它的历史事实，也不会改变“我方基准”与“直接竞品”这两个概念的含义。
21. 作为用户，我希望删除组时历史快照、SKU 快照、ChangeEvent 和采集记录继续保留，只解除组和角色绑定。
22. 作为用户，我希望组级统计遵循 Asia/Shanghai 业务日和现有事件时间口径，以便首页、详情和组详情不会出现日期不一致。
23. 作为用户，我希望没有可靠销量数据时只看到库存变化事实，不看到“卖了多少件”的伪销量结论。

## Implementation Decisions

### 1. 正式业务定义

- `CompetitorGroup` 表示一个我方目标商品的竞争分析单元，而不只是文件夹。
- 一个组最多绑定一个我方基准商品；一个组可以拥有多个直接竞品。
- 我方基准商品和直接竞品都必须是可采集的 1688 商品记录。
- “我方”是商品在组内的角色，不是另一套采集对象类型。
- 直接竞品继续由用户手动加入组；V1 不自动匹配同款竞品。
- 组名继续可以使用 `A19`、`Y35` 等型号文本，但组名本身不再承担“我方链接、价格或 SKU”的数据职责。

角色语义：

| 角色 | 业务含义 | 是否计入竞品统计 |
|---|---|---|
| 我方基准商品 | 该组比较基准，最多一个 | 否 |
| 直接竞品 | 围绕我方商品维护的竞争样本 | 是 |

角色与监控状态分离：`is_active` 仍只表示是否继续监控，商品 `status` 仍表示 `unknown`、`active` 或 `offline`。绑定为我方商品不会自动开始、停止或恢复监控。

### 2. 如何表示我方商品：候选方案比较

#### 方案 A：在现有商品记录上增加组内角色（已采用并实现）

继续使用现有 `Competitor` 作为所有 1688 商品的统一监控实体，沿用现有 `group_id`。这一方案已实现：字段为 `Competitor.group_role`，正式值为 `competitor` 和 `own`，数据库约束和绑定规则见 `own-product-role-binding.md`。

优点：

- 不新建 `OwnProduct`、`OwnProductSnapshot`、`OwnSkuSnapshot`；
- 现有 `ProductSnapshot`、`SkuSnapshot`、`CollectionRun`、`ChangeEvent` 全部按同一个 `competitor_id` 复用；
- 旧商品记录默认保持直接竞品语义，历史数据不需要推断或搬迁；
- 现有采集入口已经按商品 ID 工作，不需要新增“采集我方商品”的旁路；
- 组详情通过同一套字段比较，天然避免“我方字段”和“竞品字段”口径不一致。

代价：需要在绑定、改组、删除组和约束校验时维护角色一致性。

#### 方案 B：在组上增加一个我方基准商品引用

继续使用现有 `Competitor` 和 `group_id`，但由 `CompetitorGroup` 保存一个可空的基准商品引用，通过“该商品 ID 是否等于引用 ID”推导组内角色。

优点：

- 不改变 `Competitor` 的现有字段语义；
- 旧组只需保持基准引用为空即可兼容。

代价：

- 需要额外校验被引用商品确实属于同一组；
- 组查询、竞品转组、删除组都要同步处理基准引用；
- 角色是组关系的一部分，却分散在组和商品两处，较容易出现引用与 `group_id` 不一致；
- 仍然不能复用一个独立的 OwnProduct 身份，实际采集仍依赖 `Competitor`。

#### 已采用方案

方案 A 已实现；本 Spec 后续内容以 `Competitor.group_role` 和 `own-product-role-binding.md` 的正式 contract 为准。方案 B 保留为设计背景，不是待选方案。

不推荐新建角色关联表或独立 OwnProduct 聚合根。当前只有单用户、单平台、一个商品最多属于一个组的约束，复杂关系模型会增加迁移、查询、删除和历史兼容成本。

### 3. 绑定与兼容规则

- 用户通过现有 1688 商品添加能力登记我方商品，再将其绑定到一个竞品组并设为我方基准。
- 绑定前必须确认商品属于该组；不能把其他组的商品直接指定为当前组基准。
- 同一个组已有我方基准时，新的绑定必须明确替换或先解除旧绑定；不允许静默覆盖。
- 解除绑定后，该商品仍保留为现有监控商品和历史事实，但该组回到未绑定状态。
- 旧竞品组的所有现有成员默认视为直接竞品，不从组名、商品标题、店铺名或价格猜测我方商品。
- 旧组没有基准时，仍可查看现有 Summary、竞品列表和单个竞品详情；进入 Group Intelligence 时显示未绑定状态，并不生成我方对比结论。
- 删除组时解除组成员关系和组内角色关系；商品、快照、SKU 快照、ChangeEvent、CollectionRun、监控状态全部保留。
- `group_id = NULL` 仍表示未分组。未分组不是一个 Group Intelligence 分析单元，不自动生成“未分组的我方基准”。

### 4. 我方商品复用的事实范围

我方基准商品复用现有商品事实，不另建对应快照：

| 事实 | 来源 | Group Intelligence 用途 |
|---|---|---|
| 商品身份、链接、平台、店铺、当前状态 | `Competitor` / 最新快照 | 标识我方商品与采集状态 |
| 商品价格区间 | 最新 `ProductSnapshot.price_min` / `price_max` | 我方价格位置与价格差距 |
| 最小起批量 | 最新 `ProductSnapshot.min_order_quantity` | 起批量差距 |
| SKU 数量 | 最新 `ProductSnapshot` 下的 `SkuSnapshot` 数量 | SKU 规模比较 |
| SKU 当前页面展示价格 | `SkuSnapshot.price` | SKU 价格事实与已实现的价格变化事件 |
| SKU 库存 | `SkuSnapshot.stock` | 完整库存位置与 SKU 库存事实 |
| 商品主图、标题、上下架状态 | 最新快照与现有 `Competitor` 摘要 | 横向识别与内容 / 生命周期变化 |
| 采集时间 | `captured_at` / `last_collected_at` | 判断数据新鲜度，不伪装为实时 |

规则：

- 价格缺失保持 `NULL`，不换算为 0；
- 起批量缺失保持未知；
- SKU 数量只来自最新有效快照，不从标题、页面文案或历史数量推断；
- 商品总库存只有在至少有一个 SKU 且所有 SKU 库存均为非 `NULL` 非负整数时才可计算；
- 任一 SKU 库存未知时，商品总库存为未知；
- `0` 是有效库存，不是未知；
- 我方商品没有有效快照时，所有比较字段显示未采集，不回填历史以外的默认值；
- 采集失败、验证页、登录页、空白页或解析失败不能生成新的我方商品事实。

### 5. Group Detail V1 要回答的问题

Group Detail 不是大型数据大屏，也不重新实现商品管理。页面必须围绕一个组回答以下五类问题。

#### 5.1 我方商品概览

回答：“我方当前是什么事实状态？”

至少包含：

- 组名和绑定状态；
- 我方商品标题、店铺、链接入口、商品状态、监控状态；
- 当前价格区间；
- 当前最小起批量；
- 当前 SKU 数量；
- 当前完整总库存或未知；
- 最近成功采集时间；
- 我方商品最近发生的客观变化入口。

不在此区域显示竞争力分数、风险标签或自动建议。

#### 5.2 今日竞争变化

回答：“今天这个组有哪些客观变化？”

- 按 Asia/Shanghai 业务日筛选 `ChangeEvent.detected_at`；
- 以当前属于该组的成员为范围；不重建历史组成员关系；
- 直接竞品的变化计入“竞品变化数”；我方商品变化单独标记，不计入竞品变化数；
- 同一竞品当天多条事件保留事件数，并按事件领域聚合展示；
- 至少支持价格、商品库存、SKU、起批量、上下架、标题、主图事件的事实表达；
- 事件排序使用检测时间和稳定 ID，不把数据库插入顺序解释为重要程度；
- `detected_at` 表示系统检测时间，不表示平台真实发生时间。

组级摘要应能表达类似“3 个竞品发生变化、1 家降价、1 个 SKU 售罄”的事实，但不得把摘要变成新的 ChangeEvent。

#### 5.3 我方 vs 竞品横向比较

回答：“我方与每个直接竞品当前分别是什么状态？”

业务字段至少包括：

| 商品 | 角色 | 价格 | 起批量 | SKU | 库存 | 最近变化 |
|---|---|---|---|---|---|---|
| 我方或竞品商品 | 我方基准 / 直接竞品 | 最新价格区间 | 最新最小起批量 | 最新快照 SKU 数量 | 完整总库存或未知 | 最近 ChangeEvent 或未采集 |

补充规则：

- 横向比较使用各商品自己的最新有效快照，不要求所有商品同一时刻采集；
- 每行必须标明采集时间或能够进入详情查看采集时间，避免把过期值当作实时值；
- 商品下架仍保留历史事实，并明确显示当前 offline；
- 监控停止不等于删除，仍可显示该商品最后有效事实和监控状态；
- 无快照、字段缺失或库存不完整时保持未采集 / 未知，不补齐虚假值。

#### 5.4 近 7 / 30 天竞争动作

回答：“最近谁动作最多，动作是什么？”

- 统计当前组成员在最近 7 天和 30 天内的真实 ChangeEvent；
- 按商品统计事件总数，并拆分价格、库存、SKU、起批量、生命周期、标题、主图等领域；
- 直接竞品按事件总数降序，事件数相同时按最近事件时间降序，再以稳定商品 ID 兜底；
- 允许用户进入单个竞品详情查看事件证据；
- “动作最多”只表示事件数量最多，不等同于竞争力最高、风险最高或最危险；
- 统计边界采用现有业务日口径，不把自然日期和 UTC 日期混用。

#### 5.5 竞品入口

回答：“我要如何继续查看或管理具体商品？”

- 可进入现有 Competitor Detail 查看快照、SKU、趋势、变化和采集记录；
- 可进入现有 Competitor List 查看、筛选、分组、停止或恢复监控；
- Group Detail 不重复实现批量采集、删除、编辑商品或新的商品管理流程；
- 同款竞品仍由用户手动加入，不提供自动匹配。

### 6. 事实差距的计算边界

V1 可以给出事实差距，但不做建议。

#### 价格

- 只有我方和竞品价格两侧都可比较时才判断位置；
- 单值价格视为 `min = max`；
- 竞品价格区间的上界低于我方价格区间下界时，才计为“明确低于我方”；
- 竞品价格区间下界高于我方价格区间上界时，才计为“明确高于我方”；
- 区间重叠、只有一侧边界或任一侧缺失时，标记为重叠 / 未知，不强行归类；
- 价格位置只基于当前快照，不把 ChangeEvent 方向当作当前价格。

#### 起批量

- 两侧均有合法 `min_order_quantity` 时才比较；
- `competitor < own` 才计为“竞品起批量低于我方”；
- 任一侧未采集时不计入低于 / 高于统计。

#### SKU 数量

- 两侧都有有效最新快照时才比较；
- 竞品 SKU 数量大于我方时计为“竞品 SKU 更多”；
- 没有快照时显示未采集，不将缺失当作 0。

#### 库存

- 仅比较完整可计算的商品总库存；
- 可输出竞品完整库存的已知范围、低于 / 高于我方的数量和未知数量；
- 任一侧库存不完整时不做方向性结论；
- 库存下降只表示库存下降，不表示销量或成交量下降。

### 7. 今日和历史聚合规则

- 今日范围使用现有 Asia/Shanghai 业务日半开区间；
- 7 / 30 天范围使用同一业务日边界；
- 事件按当前 `group_id` 关系聚合，不新增组成员历史表；
- 当前属于该组的商品，其历史事件可以进入该组的历史动作统计；系统不声称这些事件发生时它一定已经属于该组；
- `is_active` 不改变历史事件是否存在；组级事实统计应明确显示监控状态，不因停止监控而把历史事件抹掉；
- 同一次采集产生的多个客观变化分别计数，页面可按商品和事件领域聚合；
- 无事件返回空集合和 0 计数，不使用虚假默认事件。

### 8. ChangeEvent V2 当前能力

ChangeEvent V2 已实现。当前正式事件模型以 `docs/specs/detect-competitor-changes.md` 和当前 ORM 为准：14 种 V2 事件及历史 legacy `stock_changed` 兼容读取均已具备。Group Intelligence 必须消费统一 ChangeEvent，不在页面层重复推断事件。

#### 8.1 起批量变化：已实现的 V2 方向事件

结论：已按正式 V2 contract 实现。

原因：

- 起批量是 Group Detail 横向比较的明确字段；
- 现有 `ProductSnapshot.min_order_quantity` 已保存事实；
- 起批量从 2 变为 5 或从 5 变为 1，是直接影响竞争环境的客观动作；
- 如果只有最新快照，没有 ChangeEvent，今日变化和近 7 / 30 天动作会漏掉该动作。

正式事件使用两个商品级方向类型：`min_order_quantity_decrease`、`min_order_quantity_increase`，`entity_key = NULL`。同一商品相邻有效快照的两侧起批量都已采集且数值不同，按方向生成事件；任一侧为 NULL、首次采集或恢复上架首轮，不猜测变化。

#### 8.2 SKU 价格变化：已实现的统一价格事件

结论：已纳入 V2 并实现；商品级和 SKU 级价格复用统一事件类型。

场景：商品整体 `price_min / price_max` 没有变化，但某个 SKU 的页面展示价格单独下降。对 1688 运营而言，这仍可能是竞争商品的实际价格动作。

建议的边界：

- 只比较相邻有效快照中同一 `sku_id`；
- 两侧 SKU 价格均非 NULL 且不同才产生事件；
- SKU 新增 / 删除不同时伪造价格变化；
- 两侧价格缺失不猜；
- 事件必须明确这是 SKU 当前页面展示价格，不宣称是所有促销体系下的最终成交价；
- 复用 `price_increase` / `price_decrease`，不新增 `sku_price_increase` / `sku_price_decrease`；
- `entity_key = sku_id`，old/new 保存 SKU 当前页面展示价格。

Group Intelligence 应直接消费这些统一价格事件，而不是让前端临时比较两个快照。

#### 8.3 SKU 普通库存变化：已实现的方向事件

结论：V2 已实现 SKU 库存方向、售罄和恢复有货事件；历史 `stock_changed` 保留兼容读取，不应删除或降级。

场景：黑色库存 `100 → 0`、白色库存 `100 → 200` 可由售罄 / 恢复或总库存部分表达；更关键的场景是黑色 `500 → 400`、白色 `500 → 600`，商品总库存保持不变。当前只看商品总库存会遗漏库存结构发生变化。

建议的边界：

- 只比较同一 `sku_id`；
- 两侧库存都为非 NULL，且都是正数；
- 数值不同才产生普通 SKU 库存变化，`>0 → 0` 仍只生成 `sku_sold_out`，`0 → >0` 仍只生成 `sku_restocked`；
- SKU 新增 / 删除不同时产生普通库存变化；
- `NULL` 不视为 0；
- 事件保存 SKU ID 和旧 / 新库存，以便 Group Detail 说明具体 SKU 动作；
- 不增加库存阈值、重要度或风险判定，先保留可靠客观变化。

正式事件复用 `stock_increase` / `stock_decrease`，`entity_key = sku_id`。这是支持“哪家库存结构发生明显变化”和动作统计的基础事实；不是新增一套能力，也不能由组详情临时推断。

#### 8.4 当前 V2 事件的复用

组级读取应复用以下已实现事件语义：

- 商品价格上涨 / 下降；
- SKU 普通库存上涨 / 下降；
- SKU 新增 / 删除 / 售罄 / 恢复有货；
- 商品下架 / 恢复上架；
- 标题变化；
- 主图变化。

历史 legacy `stock_changed` 必须保留可读性，不通过组页面猜测其方向。新旧事件兼容应由 ChangeEvent 消费层统一处理；商品总库存仍是 Snapshot 派生展示指标，不是额外 ChangeEvent。

### 9. 销量边界

- V1 可以记录未来希望分析销量、成交趋势和销售速度，但不将其作为当前 Group Intelligence 指标。
- 没有可靠且口径稳定的数据源时，不新增销量快照、销量事件或销量趋势结论。
- 库存下降只显示为“库存下降 X”，不得显示为“卖出 X”。
- 采购助手或其他外部数据若未来接入，也必须先确认口径，再单独定义事实模型和事件，不在本 Spec 偷渡。

### 10. 页面角色的长期分工

本轮不重新设计 Dashboard，只冻结长期分工：

| 页面 | 长期角色 |
|---|---|
| Dashboard | 关注“哪些我方商品组今天值得进入查看”，逐步从竞品事件列表升级为组级关注入口 |
| Groups | 管理组、绑定我方基准、查看组级入口和基本状态 |
| Group Detail | 日常竞争分析核心页，回答我方位置、今日变化、横向比较和近 7 / 30 天动作 |
| Competitor List | 监控对象管理页：搜索、筛选、分组、停止 / 恢复监控和进入详情 |
| Competitor Detail | 单个商品的证据页：快照、SKU、趋势、ChangeEvent 和采集记录 |

未来 Dashboard 的组级摘要可以表达：

```text
A19：3 个竞品发生变化，1 家降价，1 个 SKU 售罄
Y35：1 家商品下架，2 家调整价格
```

这只是长期方向，不属于本轮 Dashboard 实现或视觉设计。

### 11. 后续实现的最高 seam

优先在现有采集 → Snapshot → ChangeEvent → 查询 API 链路上完成 Group Intelligence，不新增平行采集链路。

- 角色绑定 seam：现有商品与竞品组关系管理；
- 事实 seam：现有 `ProductSnapshot` / `SkuSnapshot`；
- 事件 seam：现有 ChangeEvent 检测与保存事务，先完成事件扩展再做组聚合；
- 查询 seam：新增一个组级分析读取 contract，聚合现有事实，不把聚合结果回写为事件；
- 前端 seam：现有 Groups、List、Detail 导航和 API 请求模式，新增 Group Detail 只消费组级 contract。

## Testing Decisions

本轮不新增或修改测试。正式实现时，测试应验证用户可见的业务行为、数据保留和 contract，而不是绑定 SQL 拼接、私有 helper 或具体组件结构。

### 角色与历史兼容

- 旧组无基准时仍可读取、重命名、删除、查看竞品和历史数据；
- 旧成员默认是直接竞品，不自动猜测我方商品；
- 一个组最多一个我方基准；重复绑定必须有明确错误或显式替换流程；
- 绑定、解除、转组、删除组不会删除 Snapshot、SKU Snapshot、ChangeEvent 或 CollectionRun；
- 删除组后商品成为未分组，组内角色关系被解除。

### 事实与对比

- 最新快照选择沿用当前稳定排序：`captured_at DESC, id DESC`；
- 价格缺失、区间重叠、起批量缺失、SKU 无快照和库存不完整均保持未知语义；
- 完整库存可以计算，0 可以参与计算；
- 不完整库存不被当作 0；
- 我方与竞品使用同一字段和同一采集口径；
- 当前快照、组详情对比和单个竞品详情之间的字段值一致。

### 事件与聚合

- 今日范围正确遵循 Asia/Shanghai 业务日；
- 7 / 30 天事件按当前组成员聚合，并按事件条数和类型保留客观事实；
- 同一竞品多事件不重复计算竞品数量，但事件总数不丢失；
- 我方事件与竞品事件在角色统计中分开；
- 起批量、SKU 价格和普通 SKU 库存事件规则已经由 `docs/specs/detect-competitor-changes.md` 正式冻结；后续实现应直接按正式 ChangeEvent V2 contract 测试和消费，不允许页面自行重新判断事件语义；
- 历史 legacy 事件可读，不由消费者猜测方向；
- 没有事件时返回真实空集合或 NULL，不填充虚假变化。

### 现有测试先例

正式实现应沿用当前后端 TestClient + 临时 SQLite、migration / CHECK 约束、collection service、ChangeEvent、Dashboard、Detail 和 Groups 测试 seam；前端沿用现有 API mock、纯函数和静态渲染测试方式。优先写跨模块的可观察行为测试，不为每个一次性聚合 helper 单独建立测试套件。

## Acceptance Criteria

1. Group Intelligence V1 的正式业务单元是“一个我方真实 1688 商品 + 多个直接竞品”。
2. 一个组最多绑定一个我方基准商品；绑定关系与 `is_active`、商品 `status` 相互独立。
3. 我方商品与竞品复用同一套 Competitor、ProductSnapshot、SkuSnapshot、CollectionRun 和 ChangeEvent 事实链路。
4. 不新增 OwnProduct、OwnProductSnapshot 或 OwnSkuSnapshot 平行数据体系作为默认方案。
5. 旧组未绑定我方商品时仍兼容；系统不从组名、标题、店铺或价格猜测基准商品。
6. 未绑定组能明确显示未绑定状态，并继续支持现有分组管理和竞品查看。
7. Group Detail 的信息架构至少包含我方商品概览、今日竞争变化、横向比较、近 7 / 30 天动作和竞品入口。
8. 横向比较至少包含商品、角色、价格、起批量、SKU、库存和最近变化。
9. 价格、起批量、SKU 数量和库存均来自最新有效快照；缺失值保持未采集 / 未知。
10. 完整库存按 SKU 库存求和；任一库存未知时不计算总库存；库存下降不等同于销量。
11. 今日聚合使用 Asia/Shanghai 业务日，并区分我方变化与直接竞品变化。
12. 7 / 30 天动作按真实 ChangeEvent 统计，能够表达事件总数和按领域的分布。
13. “动作最多”仅表示客观事件数量最多，不输出竞争力、风险或建议。
14. 明确价格低于、高于、重叠和未知的边界已冻结，不对区间重叠作强结论。
15. 起批量变化使用已冻结的 `min_order_quantity_increase` / `min_order_quantity_decrease` 正式 ChangeEvent。
16. SKU 价格变化使用已冻结的 `price_increase` / `price_decrease`，并以 `entity_key = sku_id` 表示 SKU 层级。
17. 同一商品 SKU 普通库存的非零变化使用已冻结的 `stock_increase` / `stock_decrease`，并以 `entity_key = sku_id` 表示；`>0 → 0` 只使用 `sku_sold_out`，`0 → >0` 只使用 `sku_restocked`，SKU 新增 / 删除不同时生成普通库存事件。
18. Group Intelligence 后续实现直接依赖已经冻结的 ChangeEvent V2 Spec，不再重新定义事件模型。
19. Dashboard、Groups、List、Detail 和 Group Detail 的长期职责边界明确，当前 Dashboard 不因本 Spec 直接重做。
20. 实现完成前不修改长期产品文档；实现和真实运行验证后再同步“当前已实现”内容。

## Out of Scope

本 Spec 明确不做：

- AI 自动决策、AI 运营建议、自动降价建议；
- 竞争力评分、风险评分、重要度评分；
- 自动修改我方商品、自动选品、自动上架；
- 自动匹配同款竞品；
- 提醒系统、邮件、微信或其他通知；
- 报表导出；
- 多平台；
- 销量、成交趋势或销售速度的伪造与推断；
- 新采集 POC、平行 OwnProduct 采集链路或复杂推荐算法；
- 多对多竞品关系、跨组历史成员审计和复杂领域模型；
