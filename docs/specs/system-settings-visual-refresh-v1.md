# 系统设置视觉改版 V1

状态：已通过 ChatGPT Spec Review；已 Freeze，授权进入实现。

## Problem Statement

系统设置已具备基础设置与竞品监控两个独立模块，但当前卡片容器、提示块和蓝紫雾感装饰削弱了设置项的扫描效率；自动采集策略及错过计划的 Select 也不便同时比较选项含义。需要以本轮用户提供的 SaaS 设置页参考图为方向，提高信息层级、控件一致性和成熟后台感，而不改变任何设置或采集行为。

## Solution

仅将系统设置作为新视觉语言的试点：保留 Personal Workbench 全局侧边栏与现有顶部工作台区域，形成“全局导航 → 设置二级导航 → 当前模块内容”的桌面三栏空间。内容使用白色 / 极浅冷灰底、细边框、分割线和留白，以横向设置 Row 为主体；竞品监控继续分为采集节奏、风控处理、自动采集，两个枚举选择改为带说明的 Radio。

本 Spec 仅局部替代既有设置 Spec 中对应页面的卡片和 Select 展示要求；业务合同继承[竞品监控设置与采集节奏 V1](competitor-monitoring-settings-v1.md)及其后续扩展[Daily 自动采集策略 V1](daily-auto-collection-strategy-v1.md)。完整保存对象以当前已实现的九项为准，不退回早期五项版本。

## User Stories

1. 作为工作台用户，我希望继续使用熟悉的全局导航，以便明确当前仍在个人工作台内。
2. 作为工作台用户，我希望清楚区分设置模块导航和当前内容，以便快速切换基础设置与竞品监控。
3. 作为工作台用户，我希望设置名称、说明和控件在横向行中对齐，以便快速扫描和编辑。
4. 作为工作台用户，我希望采集节奏、风控处理、自动采集有轻量分组，以便理解它们的业务关系。
5. 作为工作台用户，我希望同时看到两种自动采集策略及解释，以便理解并选择适合的策略。
6. 作为工作台用户，我希望固定时间下直观看到补采与跳过的区别，以便选择错过计划的处理方式。
7. 作为工作台用户，我希望切换策略后固定时间及错过策略仍被保留，以便切回来继续编辑。
8. 作为工作台用户，我希望只保存当前模块，以免另一模块的编辑或错误影响本次保存。
9. 作为工作台用户，我希望继续看到加载、重试、保存中及成功失败反馈，以便确认操作结果。
10. 作为工作台用户，我希望保留店铺修改确认，以便理解商品身份重新识别的影响。
11. 作为键盘用户，我希望导航、Switch、Radio 和表单仍可操作且焦点可见，以便不依赖鼠标完成设置。
12. 作为产品负责人，我希望先人工验收设置页的视觉效果，以便决定是否另行讨论全局推广。

## Implementation Decisions

### 1. 试点范围与全局边界

- 仅改系统设置的 Frontend / UX：页面结构、设置页局部样式、控件表达与必要的无障碍标记。复用现有 Settings 页面、状态、保存回调和 API seam。
- 这是对 UI System 中设置页装饰与控件外观的明确局部试点例外；全局基线仍有效，品牌、信息架构、顶部工作台区域、语义状态色及其他页面不变。不得修改全局样式使其他页面一起改版。
- 不照搬参考图的顶部 SaaS 导航、搜索、通知、头像、大型平台结构、品牌和示例数据；现有工作台顶部区域继续沿用，不新增入口或功能。
- 不建设通用组件库、Design Token 平台或 Storybook，不新增依赖，不顺手重构 App、状态管理或 API 层。优先现有结构、局部 CSS 和原生表单控件。

### 2. 布局和信息层级

- 桌面三栏依次为现有全局侧边栏、仅包含“基础设置 / 竞品监控”的二级导航、当前模块内容。二级导航有明确当前选中态，内容标题与当前模块一致；初次进入仍默认基础设置。
- 设置区域使用大面积白色 / 极浅冷灰背景，弱化毛玻璃、蓝紫渐变、阴影及卡片套卡片。允许一个轻量内容边界，不给每个字段创建卡片，不将三组竞品设置做成三张重卡片。
- 设置项优先横向 Row：左侧名称及简短说明，右侧控件；单位、有效范围、推荐值就近呈现为次级文字，不与设置名称争夺注意力，不丢失业务提示。
- 竞品监控按“采集节奏 → 风控处理 → 自动采集”顺序排列，组间主要用标题、留白和分割线建立层级。
- 控件紧凑、统一、小圆角；同类输入高度、文本基线、控件列对齐和行间距一致。蓝色主要用于选中态、Radio、Switch、Focus 和 Primary Button；错误和成功继续使用现有语义提示，不能只靠颜色表达。
- 沿用现有间距尺度和字体。桌面优先，窄屏允许导航和 Row 自然折叠，保证文字、控件及操作区可见可用；不要求移动端新设计。沿用现有主滚动行为，不新增多重内部滚动或 JS 滚动控制。

### 3. 字段与保存合同不变

基础设置保留我方店铺名称、精确匹配及空白标准化说明、未配置提示、255 字符输入上限、空白不可提交、返回大屏和原有修改确认。继续独立调用 `GET / PUT /api/settings/own-shop-name`，PUT 仅提交 `own_shop_name`；确认取消时不发出保存请求。成功后的身份重新识别、关联数据刷新及刷新失败警告保持原语义，不将“保存成功但刷新失败”误报成保存失败或无条件成功。

竞品监控继续独立调用 `GET / PUT /api/settings/competitor-monitoring`，一次提交完整九项，不拆为组级保存或自动采集专用 API：

| 分组 | API 字段 | 展示 / contract |
| --- | --- | --- |
| 采集节奏 | `item_interval_seconds` | 整数秒，1～60 |
| 采集节奏 | `continuous_collection_count` | 整数数量，1～50 |
| 采集节奏 | `batch_rest_seconds` | 整数分钟，0～30；保存乘 60 为整数秒；0 关闭主动休息 |
| 风控处理 | `verification_cooldown_seconds` | 整数分钟，1～60；保存乘 60 为整数秒 |
| 风控处理 | `auto_resume_max` | 整数次数，0～5；0 直接进入人工处理 |
| 自动采集 | `auto_collection_enabled` | Switch，JSON boolean |
| 自动采集 | `auto_collection_strategy` | Radio，`rolling_24h / fixed_daily` |
| 自动采集 | `auto_collection_time` | 原生 Time Input，严格 `HH:mm` |
| 自动采集 | `auto_collection_missed_policy` | Radio，`catch_up / skip` |

默认值、校验范围、单位换算、完整 body、原子事务、Backend 权威校验和成功响应回填均不变。禁止新增字段、改名或改变值类型，禁止从运行中 Batch 快照替代当前已保存设置。

### 4. Radio 表达与条件显示

自动采集策略改为一个互斥 Radio 组，每项包含名称和一句真实业务解释：

- **滚动 24 小时** → `rolling_24h`：商品无采集记录，或距最近一次采集尝试已满 24 小时，才进入自动采集范围；失败尝试也计入。
- **每日固定时间** → `fixed_daily`：按运行 Backend 的电脑本地时间每日判断采集，计划时间后已尝试的商品当天不再重复自动采集。

仅 `fixed_daily` 显示时间输入及“错过计划”Radio 组：

- **下次启动时补采** → `catch_up`：计划后启动或启用固定策略时，补采当天计划后尚未尝试的商品。
- **本次跳过** → `skip`：计划后才启动或启用固定策略时跳过当天；计划前已运行并跨过计划点的任务遇忙仍按原规则等待后续检查。

这些说明不得承诺 Backend 未运行时执行、失败立即重试、关闭自动采集停止当前 Batch，或省略 skip 的既有例外。保留“自动采集使用上方的采集节奏与风控设置。”及当前运行任务不变的提示；说明应区分 Batch 节奏快照与自动调度对后续检查生效的语义。

显示条件只由 strategy 决定，不能因 Switch 关闭而新增隐藏或禁用策略编辑的规则。切到 `rolling_24h` 仅隐藏 fixed-only 编辑 UI，保留当前草稿时间和 missed policy，并仍随完整九项 PUT 保存；切回 `fixed_daily` 恢复原值。关闭 Switch 不清空这些值。

### 5. 状态、操作区与可访问性

- 基础设置与竞品监控保留独立 loading、load error、save error、submitting 和保存反馈。竞品监控继续首次打开时懒加载，已成功加载后切换模块不因视觉改版新增请求或重置草稿；失败仍可在本模块重试。
- 一块加载或保存失败不覆盖另一块已加载内容、编辑值或错误；二级导航仍可切换查看另一模块。不合并模块状态或提交锁。
- 当前模块底部设置轻量操作区，可借鉴参考图的对齐、细分割线和白色背景；保存按钮只提交当前模块。基础设置保留返回大屏，不新增参考图的取消、重置、全局保存或自动保存行为。
- 提交中保留“保存中…”和现有控件 / 操作禁用，防止重复提交；成功使用既有通知，失败保留本模块错误和可继续编辑的值。Loading / Error / Success / Submitting、确认提示均不得因布局变化被遮挡。
- 导航可用键盘操作且当前项可识别；Switch 有可读名称和 checked 状态；两个 Radio 组各有组名、独立分组和每项标签，支持原生 Tab、方向键及 Space 操作。说明与控件正确关联，Focus 可见，错误继续可被辅助技术识别。不用无语义可点击元素替代原生控件。

## Testing Decisions

只测试外部行为，不断言 CSS 类名、DOM 层数、精确像素、颜色值或布局实现。优先沿用已有最高层浏览器交互与请求 seam，不新增测试专用 API 或重复搭建测试架构。

- 复用 `frontend/src/App.test.tsx` 的 Settings Frontend 场景：已有真实挂载页面、Vite / Chromium 和请求 mock，覆盖基础 / 竞品加载与保存错误隔离。其现有设置 fixture 仍只有五项；实现阶段应仅在相关场景补齐九项 fixture，避免旧 mock 掩盖 contract 回归。
- 复用 `frontend/e2e/competitor-monitoring-settings.spec.ts`：已有懒加载、数字单位换算、完整九项 PUT、fixed-only 隐藏及值保留、保存成功路径。将 Select 操作更新为按可访问名称选择 Radio，保留已有请求断言，并增量保护两个枚举及切回 fixed 的值恢复，不重写整套 E2E。
- 复用 `frontend/e2e/support/api-mock.ts` 的默认拒绝未声明 `/api/**` seam；使用九项显式 fixture / 现有 route override，在导航前安装 mock，并检查无意外 API。不得访问真实 Backend、工作数据库或外部采集网站。

实现阶段应通过现有测试或最少增量场景证明：

1. 基础设置 / 竞品监控切换、默认模块、竞品懒加载及成功加载后草稿保留不变。
2. 两个模块 loading、加载失败 / 重试、保存失败继续隔离；另一模块已加载值不会被替换。
3. 保存只调用当前模块 endpoint；竞品保存一次且包含九项正确类型与值，两个分钟字段仍准确转秒。
4. 两种策略 Radio 的选中状态与 API value 一致；两个错过策略 Radio 同样对应 `catch_up / skip`，至少验证两组选项均可选择。
5. rolling 隐藏 fixed-only 控件；fixed 显示；编辑时间和 policy 后切到 rolling 再切回，值仍保留；隐藏值仍随完整保存提交。开关关闭不清空配置。
6. submitting 禁止重复保存、控件禁用、成功反馈和失败后错误 / 草稿保留不回归；基础设置修改确认取消不 PUT，保存后的刷新失败继续给出原有警告。
7. Radio 可通过键盘切换并保存对应值，Switch 的可读名称及状态、Focus 和现有表单键盘交互可用。

实现交付运行相关 Settings Frontend 测试、既有设置 Playwright 路径、Frontend 类型检查 / 构建及 `git diff --check`。Backend 合同未变，不为本视觉 Feature 新增 scheduler、事务或数据库测试；已有业务测试继续有效。

### 人工视觉验收

自动行为测试不能替代视觉验收。用户在桌面实际查看基础设置、竞品监控及 fixed_daily 展开状态，并抽查窄屏、加载 / 错误 / 保存反馈：

- 全局导航、设置二级导航、内容三栏层级清楚，当前模块易识别。
- 相比改版前明显减少卡片堆叠、毛玻璃和渐变装饰，三组内容仍清晰。
- 设置行易快速扫描，名称 / 说明与控件关系明确，范围、单位和 Radio 解释可读。
- 控件尺寸、对齐、间距和小圆角一致，长解释不挤压控件，窄屏无遮挡。
- 蓝色使用克制，主要集中于交互态与主要操作；焦点与禁用状态仍可辨认。
- 品牌、全局导航和工作台骨架使页面仍明显属于 Personal Workbench，没有直接复制参考 SaaS。
- 底部操作区归属当前模块，滚动时不遮挡最后一行或状态反馈。

不要求截图逐像素复刻参考图；视觉通过由用户确认，不能以测试通过自行宣布通过或推广。

## Out of Scope

- Backend、API、数据库、设置字段、保存事务、采集业务规则、Runner / scheduler / polling 改动。
- 统一全局保存、分组单独保存、自动保存、取消 / 重置新语义、新设置模块。
- 验证码自动识别、人工打码、请求超时、采集时间窗口及参考图其他现有产品没有的功能。
- 全局侧边栏 / 顶部平台结构重做、其他页面改版、App / 状态 / API 架构重构。
- 通用组件库、Design Token 平台、Storybook、新依赖、完整移动端系统。
- 修改 `docs/ui-system.md` 或其他文档、提前升级全局视觉基线。

## Further Notes

参考图仅提供布局、信息密度与控件语言方向，其中字段、数字、时间和平台入口均不是产品事实或新增需求。本轮不另存参考素材，不把临时附件路径作为实现依赖。

本轮纯 Spec 交付仅新增本文，自检范围、当前实现兼容性和测试要求后，仅 Commit / Push 本 Spec；按[协作方式](../roadmap/vibe%20coding协作方式.md)进入 ChatGPT Spec Review，通过后才 Freeze 并另行授权实现。用户实际验收系统设置且决定推广后，才另行讨论全局 UI System 升级。
